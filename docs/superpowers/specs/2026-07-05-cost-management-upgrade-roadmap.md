# 주문/매출 > 수익·원가 메뉴 업그레이드 로드맵

> 작성일: 2026-07-05
> 대상: `/orders` → `cost`(수익·원가) 서브탭 및 `/api/cost-management/*`
> 목적: 검증(verification) 리포트. 발견된 개선 후보를 영향도 기준으로 정렬하고 단계별 실행 순서를 제시한다. 구현은 이후 각 항목을 별도 스펙 → 플랜으로 분해해 진행한다.

---

## 0. 요약

수익·원가 메뉴는 멀티채널(쿠팡 윙 / 로켓그로스(RG) / 네이버) 셀러의 **상품별 원가·재고·FIFO 실현손익 관리 대시보드**다. 기능은 이미 폭넓게 구현돼 있으나, 사용자 체감상 **UX가 가장 큰 문제**이며 그다음으로 **계산 정합성(숫자 신뢰도)** 이슈가 시급하다.

우선순위 결론:

| Phase | 성격 | 왜 이 순서인가 |
|---|---|---|
| **P1** | UX — 테이블 가독성 / 임포트·새로고침 투명성 / 피드백·오류 처리 | 매일 보는 화면. 여기서 막히면 나머지 기능이 아무리 정확해도 안 쓰게 된다. |
| **P2** | 계산 정합성 | "숫자가 실제로 틀리는 버그" 포함. 대시보드를 믿고 쓰려면 필수. **UX와 병행 권장.** |
| **P3** | 성능·확장성 | 판매 이력이 쌓일수록 선형 악화. 지금은 견디지만 방치하면 P1 개선을 무력화. |
| **P4** | 설계·보안 정리 | 위생(hygiene) 이슈. 사고 예방 성격. |

**지금 당장 3선** (P1 중 임팩트 높고 작업량 낮음):
1. 임포트/새로고침 결과 요약 피드백 (몇 건 신규/보정/스킵) — §1.2
2. 서브탭 URL 딥링크 (새로고침·공유 시 탭 유지) — §1.2
3. 테이블 KPI 우선 재편 (핵심 3열 고정 + 운영열 접기) — §1.1

- **영향도**: 셀러가 보는 숫자/경험에 미치는 파급. ★★★(최상) ~ ★(낮음)

- **위험도**: 데이터 마이그레이션·회귀 위험. 低 / 中 / 高

## P1 — UX (체감 최우선)

### 1.1 테이블이 한눈에 안 들어옴

**문제**
- 테이블 열이 약 17~19개(채널·상품명·원가·배송비·RG배송비·재고·재고가치·실현손익·마진율·광고비·ROAS·위너·입고·판매·내역·[RG실재고]·숨김·삭제). 핵심 KPI(**실현손익·재고·ROAS**)가 운영용 열(입고/판매/내역 버튼 등) 사이에 묻힌다.
- 그룹행은 열 13~15가 대부분 빈 칸이라 시각적 노이즈가 큼 (`CostManagementTab.tsx:632-693`).
- 폰트가 8~9px 라벨까지 섞여 밀도가 과함. 색상 코드(초록/빨강/파랑/보라)가 규칙 없이 많아 위계가 흐림.
- 상단에 **매출 개념이 둘** 병렬로 존재: "실제 매출(API·5카드, `:951-1005`)"과 "원가·수익(수동입력·3카드, `:1010-1029`)". 어느 숫자가 '진짜'인지 사용자가 헷갈릴 여지.

**근거**: `src/components/orders/CostManagementTab.tsx:588-705`(그룹/헤더 열 정의), `:708-780`(자식행), `:925-1029`(2종 요약카드)

**영향**: 매일 여는 메인 화면의 정보 위계가 약해 "지금 뭐가 중요한지"를 빠르게 읽지 못함.

**제안 방향**
- 열을 **핵심 KPI / 운영 액션 2군으로 분리**: 실현손익·마진율·재고·ROAS는 항상 보이게, 배송비·RG배송비·재고가치·위너 등은 "상세 열 펼치기"로 접기.
- 입고/판매/내역/삭제/숨김 등 **액션 버튼은 행 우측 "⋯" 메뉴 또는 hover 액션**으로 통합해 열 수를 대폭 축소.
- 그룹행은 빈 셀 대신 **핵심 합계만 큰 글씨**로, 나머지는 생략.
- 상단 매출 2종은 "실제 매출(플랫폼 확정)" vs "관리 손익(내 입력 기반)"으로 **라벨과 관계를 명시**하고 시각적으로 묶어 혼동 제거.
- (선택) 열 표시/순서 사용자 설정 저장.

**점수**: 영향도 ★★★ / 작업량 L / 위험도 低

### 1.2 임포트·새로고침 혼란

**문제**
- 주문 가져오기(`runAllBulkImport`, `:271`)와 상품 로드(`load`, `:241`)가 **무엇을 얼마나 갱신했는지** 사용자에게 명확히 알려주지 않음. bulk import 결과(신규/보정/스킵 건수)가 요약 피드백으로 노출되지 않음.
- 서브탭이 `useState`라 **URL에 반영 안 됨** → 새로고침/공유/뒤로가기 시 항상 '주문·배송' 탭으로 리셋 (`OrdersClient.tsx:9-15`).
- 여러 채널 임포트가 병렬로 도는 동안 진행 상황 표시가 약함. 부분 실패 시 어떤 채널이 실패했는지 카드(`apiWarnings`, `:938-948`)는 있으나 임포트 자체 결과와 분리돼 있음.

**근거**: `CostManagementTab.tsx:241-370`, `OrdersClient.tsx:9-53`

**영향**: "가져오기 눌렀는데 뭐가 바뀐 거지?"라는 불확실성. 재작업·중복 클릭 유발.

**제안 방향**
- 임포트 완료 시 **채널별 결과 요약**(신규 N건 / 금액 보정 N건 / 중복 스킵 N건 / 실패 사유) 토스트 또는 패널.
- 서브탭을 URL 쿼리/경로(`?tab=cost`)로 승격 → 딥링크·새로고침 유지.
- 임포트 진행 중 채널별 스텝 인디케이터(윙→RG→네이버) 표시.
- "마지막 동기화 시각" 표기.

**점수**: 영향도 ★★★ / 작업량 M / 위험도 低 (탭 URL·결과 토스트는 각각 S)

### 1.3 피드백·오류 처리

**문제**
- `alert()`/`confirm()` 기반 피드백 다수 → 흐름 끊김, 스타일 불일치.
- 불친절한 에러: FIFO 재고 초과 시 목록은 조용히 0 표시(`products/route.ts:200-202` `console.warn` 후 0), 드로어만 422 "재고 데이터를 확인해 주세요"(`fifo-summary`). 사용자는 원인(어느 상품이 왜)을 모름.
- 판매 편집 시 쿠폰할인·채널·사이즈 수정 불가(빈 셀, `SaleEntryPanel.tsx:385, 462`).

**근거**: `SaleEntryPanel.tsx:385, 462`, `products/route.ts:200-202`, 다수 컴포넌트의 `alert`/`confirm`

**영향**: 오류가 났을 때 "어떻게 고치는지"를 안내받지 못해 데이터가 방치됨.

**제안 방향**
- `alert`/`confirm` → 인라인 토스트 + 확인 다이얼로그 컴포넌트로 통일 (P1 UX 리팩터와 함께).
- FIFO 재고 초과 상품을 **목록에서 배지/경고로 노출**하고 "판매량 > 입고량" 원인과 보정 링크(입고 추가/판매 수정) 안내.
- 판매 편집에서 쿠폰할인·채널 등 **누락 필드 편집 가능화**.

**점수**: 영향도 ★★ / 작업량 M / 위험도 低

## P2 — 계산 정합성 (숫자 신뢰도) · UX와 병행 권장

> 여기 항목 중 §2.1·§2.2는 **숫자가 실제로 틀리는 버그**다. UX와 동일 급으로 취급할 것.

### 2.1 배송비 하드코딩 불일치 ★★★ / M / 中
- 단건 임포트는 택배비 **3,500원 고정**(`coupang-import/route.ts:192, 321`)인데, 일괄 임포트(`wing-bulk-import`, `naver-bulk-import`)는 배송비를 **아예 안 넣어 0원**. → **같은 주문도 가져온 경로에 따라 실현손익이 달라짐.**
- 쿠폰할인도 bulk 경로는 항상 0으로 저장돼 단건과 불일치.
- 방향: 배송비/쿠폰 산정 로직을 **공용 함수로 단일화**하고 단건·일괄이 동일 규칙을 쓰게. 3,500원은 설정값으로 외부화.

### 2.2 취소/반품 소급 미반영 ★★★ / L / 中
- 임포트가 `ON CONFLICT DO NOTHING`/부분 UPDATE라, 임포트 후 취소·반품된 주문이 `sale_records`에 **영구 잔존**. 매출·손익이 과대 계상.
- 방향: 임포트 시 취소/반품 상태를 조회해 **soft-delete 또는 상태 컬럼으로 동기화**. (§1.2 임포트 결과 요약에 "취소 반영 N건" 포함.)

### 2.3 다운로드쿠폰 "100% 사용" 최악 가정 ★★ / M / 低
- 다운로드쿠폰 할인을 전량 사용 가정(`coupang-import/route.ts:46`)해 실현손익을 과소 추정할 수 있음.
- 방향: 실제 사용률 반영이 어렵다면 **가정치를 사용자 설정(정책)으로** 노출하고 근거를 UI에 표기.

### 2.4 소분 이월 자동 재계산 없음 ★★ / M / 中
- 소분 입고 수정/삭제 시 이월값 자동 재계산 없이 경고만(`entries/[id]/route.ts:770-775` `subdivision_carryover_stale`).
- 방향: 재계산 트리거 또는 이월 수동 보정 UI 제공.

### 2.5 (참고) 기타 정합성
- FIFO 재고 초과 조용한 실패 → **§1.3에서 UX로 처리**.
- 기간 프리셋의 로컬 타임존/UTC 혼용(`toDateStr` vs `toISOString`) → 자정 경계 오차 소지. 날짜 유틸 통일 권장. (★ / S / 低)

## P3 — 성능·확장성

### 3.1 products GET 전량 로드 ★★ / L / 中
- `products/route.ts:15~`가 유저의 **전 입고·전 판매를 매번 전량 로드** 후 앱단에서 FIFO 계산. 페이지네이션/캐시 없음 → 판매 이력 증가 시 선형 악화.
- 방향: 서버측 집계/증분 캐시 또는 상품 단위 지연 로드.

### 3.2 쿠폰할인 N+1 API 호출 ★★ / M / 中
- `coupang-import`가 판매 건별 `getOrderImmediateDiscount`를 **순차 호출**(`:335-342`).
- 방향: 배치/병렬(레이트리밋 고려) 또는 캐시.

### 3.3 개별 PATCH fan-out ★ / M / 低
- 숨김/그룹숨김이 상품 수만큼 개별 PATCH (`CostManagementTab.tsx:431-439, 485-497`).
- 방향: bulk 엔드포인트 신설.

### 3.4 coupang-products 전수 조회 부하 ★ / M / 中
- 모달 열 때마다 6상태 × 2 businessType 전수 페이지네이션. 429 위험(코드에 방지 주석 존재).
- 방향: 캐시/증분 조회.

## P4 — 설계·보안 정리

### 4.1 API 라우트 내 런타임 DDL ★★ / M / 中
- `bulk-setup-variants/route.ts` Step 1이 `ALTER TABLE` 실행(마이그레이션 우회). → 정식 마이그레이션으로 이전.

### 4.2 디버그 엔드포인트 노출 ★★ / S / 中
- `debug-coupang-coupons`가 인증만 통과하면 **stack trace 포함 200 응답**. → 제거 또는 개발 전용 가드.

### 4.3 `coupang_order_item_id` 전역 UNIQUE·네이밍 오용 ★ / L / 高
- 마이그레이션 058의 전역 UNIQUE라 멀티유저 충돌 소지. 네이버/윙 ID까지 이 컬럼에 혼재(`naver-{id}`).
- 방향: user_id 스코프 복합 UNIQUE + 채널별 식별 컬럼 분리(마이그레이션 필요, 위험도 高).

### 4.4 (참고) 죽은 필드·트랜잭션 밖 로그
- `product_costs.current_stock` 미사용(항상 FIFO 재계산). `rg_shipment_events`가 트랜잭션 밖 기록이라 유실 가능(의도된 트레이드오프). 정리 시 함께 검토.
