# Detail Builder × PRO 레이아웃 — 이미지 배치 설계

> **TL;DR** 사용자가 섹션별로 분류해 꽂아둔 사진 정보를 `generate-pro-layout`에 전달하지 않아, Claude가 「사진 4장짜리 상품」으로 알고 레이아웃을 짠다. 낱장 인덱스 대신 **그룹 이름 하나**(`sourceGroup`)를 주고받는 계약으로 바꾸고, 낱장 배치는 클라이언트 불변식으로 보장한다.

- 작성일: 2026-08-15
- 대상: `src/app/listing/detail-builder` → `src/app/api/ai/generate-pro-layout`
- 계기: 마크곤잘레스 키즈 2매 세트(사진 21장) 상세페이지 제작에서 6회 재생성

## 1. 무슨 일이 있었나

사진 21장을 8개 섹션(구성 2 · 세트 4 · 자수 4 · 등판 3 · 밑단 3 · 원단 2 · 사이즈 1 · 표시사항 2)에 꽂아둔 상태로 「Pro 템플릿으로 생성」을 실행했다.

| # | 증상 | 그때의 대응 |
|---|---|---|
| 1 | HTTP 400 — 남는 17장을 한 섹션에 몰아 보냄 (render 상한 6장) | 6장씩 분할 |
| 2 | 원단 설명 옆에 1+1 썸네일, 자수 설명 옆에 전체 제품컷 | 어휘 겹침 매칭 도입 |
| 3 | 먼저 나온 섹션이 사진을 선점 | 전역 최적 짝짓기로 교체 |
| 4 | 9장이 본문 밖 맨 뒤로 밀림 — **경고 없음** | DOM을 직접 뜯어 발견 |
| 5 | 매 실행마다 레이아웃·카피가 달라짐 | localStorage에 확정본 수동 보관 |

2·3의 대응은 증상을 덮은 것이지 원인을 고친 것이 아니다.

## 2. 원인

### 2-1. 정답지를 넘기지 않는다

`buildWithProTemplate()`은 `productImageCount`(개수)만 보내고 `productImages`는 보내지 않는다. 그러면서 응답의 `imageRef`를 **무시**하고 이미지를 순서대로 배분한다.

`system-prompt.ts:17`에는 매칭 장치가 이미 있다.

> `imageRef` = 이 슬롯에 쓸 제품 이미지의 인덱스. 제공된 이미지를 실제로 보고, 그 섹션 내용에 가장 맞는 이미지를 지정하세요.

`detail-maker-pro`는 base64를 실제로 보내 이 경로로 동작한다. Detail Builder만 장치를 죽여둔 채 클라이언트에서 추측한다.

**사용자는 업로드 시점에 이미 사진을 섹션별로 분류했다.** 그것이 매칭의 정답지인데 API에 전달되지 않는다.

### 2-2. 슬롯 총량이 애초에 부족하다 — 산수 문제

```
detail-builder/page.tsx   productImageCount: Math.min(4, 21) = 4
route.ts:220              imageCount = images.length || productImageCount = 4
route.ts:254              "제품 이미지 4장이 인덱스 0..3으로 제공됩니다"
                          "섹션 수: 최대 sectionCap(4) = 8개"
```

Claude는 **21장짜리가 아니라 4장짜리 상품으로 알고** 설계했다. 9장이 밀린 것은 매칭 실패 이전에 놓을 자리가 없었던 것이다.

`sectionCap`은 `Math.min(10, Math.max(6, imageCount * 2))`라 **상한이 10**이다. `imageCount`만 21로 고쳐도 섹션은 8 → 10으로만 늘어난다.

### 2-3. 어휘 매칭은 원리적으로 불안정하다

```ts
overlap = n / Math.max(1, Math.min(a.size, b.size))
```

짧은 지문이 포함관계이기만 하면 1.0이 된다. 임계 0.12는 실측 근거가 없다. 실제로 등판 설명의 "스트라이프" 한 단어가 세트 설명과 겹쳐 등판 사진이 세트 섹션으로 갔다.

## 3. 설계

### 3-1. 요청 — 그룹 매니페스트

`productImages`(base64, max 4)는 유지하고 텍스트 필드를 신설한다. 둘은 **상호배타**다 — 동시에 오면 `imageRef`가 base64 인덱스인지 매니페스트 인덱스인지 모호해진다. zod `refine`으로 거부한다.

```ts
groupManifest: z.array(z.object({
  key:   z.string().max(30),                 // 'emblem'
  title: z.string().max(60),                 // '가슴에 놓인 갈매기 자수'
  desc:  z.string().max(200).optional(),
  count: z.number().int().min(1),
})).max(12).default([])
```

Detail Builder의 섹션 `key` · `title` · `desc` · 장수를 그대로 옮긴다. 새로 작성할 문구가 없다.

### 3-2. 응답 — 그룹 이름 하나

섹션에 필드 하나를 추가한다.

```
sourceGroup?: "emblem"
```

낱장 인덱스를 요구하지 않는 이유: 「낱장 구매 vs 2매 세트」 비교표를 발명하는 데 필요한 정보는 *"1+1 컷이 bundle 그룹에 있다"*이지 *"index 3"*이 아니다. 섹션 재구성 능력과 낱장 인덱스는 무관하다. **12개 이하의 이름 중 하나를 고르는 것이 40개 인덱스를 중복·누락 없이 배정하는 것보다 오류 표면이 훨씬 작다.**

프롬프트 규칙은 셋이다.

1. 각 그룹을 정확히 한 섹션에 배정한다
2. 모든 그룹을 쓴다
3. 이미지가 필요 없는 서사 섹션은 `sourceGroup`을 생략한다

이 모드에서는 `imageSlots` · `imageRef` · `flux_lifestyle`을 요구하지 않는다.

### 3-3. 서버 파생값 교정

```ts
// imageCount — 매니페스트가 있으면 실제 장수
const imageCount = images.length || sumCount(groupManifest) || productImageCount;

// 섹션 상한 — 그룹 수 + 서사 섹션 여유
const cap = groupManifest.length
  ? Math.min(16, groupManifest.length + 5)
  : sectionCap(imageCount);
```

매니페스트 경로에서만 다른 식을 쓴다. 기존 경로의 동작은 바뀌지 않는다.

### 3-4. 클라이언트 배치 — 규칙이 아니라 불변식

```
sourceGroup이 유효하고 아직 안 쓰였다  → 그 그룹 큐 전체를 이 섹션에
그룹이 6장을 넘는다                    → 바로 뒤에 그리드로 이어붙임
아무 섹션도 안 가져간 그룹             → 맨 뒤 그리드 + 경고
```

Claude가 규칙을 어겨도 사진이 사라지지 않는다. **어휘 매칭 코드는 삭제한다.**

### 3-5. 렌더러 정합

`renderClaudeLayout`은 `attachedImages`를 직접 그리지 않고 `blocks`의 `{type:'image', attachedIndex}`로만 그린다. 다음 두 지점을 클라이언트에서 막는다.

**(a) 블록 부족으로 인한 무음 증발** — `normalizeImageBlocks`는 image 블록이 **0개일 때만** 1개를 주입한다. 슬롯 4개에 블록 1개면 3장이 소리 없이 사라진다. 붙인 장수만큼 블록이 있는지 확인하고 모자라면 주입한다.

**(b) option_grid 캐리어** — `isOptionGridCarrier`는 `items.length === imageCount`일 때만 카드에 이미지를 그리고, 캐리어로 판정되면 `stripImageBlocks`가 image 블록을 전부 제거한다. 장수가 어긋나면 블록도 카드도 없어 **그 섹션 이미지가 전원 미표시**된다. 캐리어 섹션에는 카드 수와 정확히 같은 장수 또는 0장만 붙인다.

### 3-6. 검증과 경고

배치율은 첨부 수가 아니라 **렌더 가능 수**로 센다(3-5 때문에 첨부 수는 과대 집계된다). 서버에 이미 있는 `imageUsageWarnings`를 확장해 응답 `warnings`로 받고 화면에 띄운다.

```
✅ 8개 그룹 21장 전부 배치
⚠️ backlogo(3장)를 아무 섹션도 가져가지 않아 맨 뒤에 붙였습니다
```

`repairProLayout`도 함께 고친다 — 지금은 매니페스트 규칙을 모른 채 섹션을 다시 써서 `sourceGroup`을 지울 수 있다.

### 3-7. 재현성 — 최소한만

재생성 직전 결과를 `detail-builder-prev-html`로 옮기고 「직전 결과로 되돌리기」 버튼 하나를 둔다. 여러 결과를 보관·비교하는 기능은 만들지 않는다 — 6회 재생성의 원인은 결과가 **달라서**가 아니라 **틀려서**였으므로, 배치가 고쳐진 뒤 필요성을 다시 판단한다.

## 5. 손대지 않는 것

`detail-maker-pro` 화면, `productImages` 경로, `render` API 스키마. 다만 섹션이 20개(render 상한)를 넘지 않도록 클라이언트가 세고 경고한다.

## 6. 검증

### 계획

- 매니페스트 있는 요청 / 없는 요청 각 1회 — 기존 `detail-maker-pro` 경로 무영향 확인
- 마크곤잘레스 재생성 — 배치율 100%, 자수 4장이 한 섹션에 모이는지
- 배치율 표시값과 DOM 실측 대조 (3-5의 무음 증발이 집계에 반영되는지)
- `option_grid` 섹션에서 카드 수 ≠ 첨부 수 상황을 일부러 만들어 미표시가 나지 않는지

### 2026-08-15 실행 결과

`tsc` 통과 · `eslint` 통과 · `detail-page` 관련 테스트 **709개 전부 통과**(37파일).

마크곤잘레스 20장으로 3회 생성한 결과, **세 번 모두 20/20 배치 · 페이지 끝으로 밀린 사진 0장**이었다. 되돌리기도 확인했다 — 3회차(32,759자)에서 버튼을 누르니 2회차(33,026자)로 복귀했고 버튼은 사라졌다. 묶음별 귀속은 다음과 같다.

| 묶음 | 붙은 섹션 |
|---|---|
| bundle 2장 | 「같은 옷을 색만 다르게 두 벌」 |
| option 4장 | 「어느 쪽을 고르셔도 두 벌이 함께」 · 「디자인은 같고 색 조합만 다름」 |
| emblem 4장 | 「몇 번을 빨아도 갈매기는 그대로」 · 「손으로 만지면 도톰하게 잡히는 결」 |
| backlogo 3장 | 「뒤에서 봐도 브랜드가 보입니다」 · 「가슴 자수와 같은 옐로우 톤」 |
| detail 3장 | 「앉아도 팔 올려도 옷이 안 당깁니다」 · 「밑단 옆선에 달린 브랜드 라벨」 |
| fabric 2장 | 「속옷이 비치지 않는 두께」 · 「면(COTTON) 100%」 |

개선 전(같은 상품, 어휘 매칭 시절)에는 원단 설명 옆에 1+1 썸네일이, 세트 설명 옆에 네이비 등판 자수가 붙었고 매 실행 5~9장이 본문 밖으로 밀렸다.

계기판 첫 판에서 결함이 하나 드러나 고쳤다 — 배치가 100%인데 ⚠️로 표시됐다. 서버의 일반 조언(「사이즈 실측을 입력하면 스펙 표로 들어갑니다」)이 배치 경고와 같은 줄에 섞였기 때문이다. **배치 결함(`notes`)과 그 밖의 조언(`hints`)을 갈라** 아이콘 판정은 전자로만 하도록 바꿨다.

## 7. 검토 이력

초안은 낱장 `imageManifest`(사진 21장 각각에 label을 붙여 Claude가 index를 지정)로 설계했다. Fable 5 검토에서 다음이 교정됐다.

| 초안 | 교정 |
|---|---|
| "PRO는 AI가 만들 이미지의 틀을 그리는 도구 — 전제가 반대" | 과장. `product_nukki`·`detail_closeup`은 실물 슬롯이고 `detail-maker-pro`는 이미 실물을 `imageRef`로 배치한다. 정확히는 **정답지 미전달** |
| (인식 못 함) | **슬롯 총량 부족** — `imageCount=4`가 `sectionCap(4)=8`로 이어져 21장을 놓을 자리가 없었다 |
| 낱장 index 배정 | **그룹 이름 하나**로 낮춤. 오류 표면 축소, "모든 사진 배치"가 프롬프트 부탁에서 코드 불변식으로 |
| 어휘 매칭을 2순위 폴백으로 유지 | 삭제. `min` 정규화 결함과 매직넘버 임계 |
| 클라이언트에 배치율 표시 신설 | 서버 `imageUsageWarnings` 확장으로 대체 |
| (인식 못 함) | 렌더러 무음 증발 · `option_grid` 캐리어 지뢰 |

검토가 놓친 것도 있어 설계에 반영했다.

- **`sectionCap` 상한 10** — `imageCount` 기준만 매니페스트로 바꿔도 섹션 수에서 다시 막힌다 (3-3)
- **무음 증발은 2026-08-15 실행에서 발생하지 않았다** — leftover 그리드가 슬롯 수만큼 블록을 만들어 우연히 맞았다. 위험은 미래형이며, 오늘의 사고 원인과 구분해야 우선순위가 흐트러지지 않는다
