# 코스트코 영수증 → 자동 입고 — 설계

> **작성일:** 2026-08-08
> **범위:** 영수증 촬영·붙여넣기 → OCR → 검토 → 수익원가 입고 확정
> **라우트:** `/m/receipt` (모바일) + 수익원가 탭 연동 (데스크톱)

---

## 1. 목적

코스트코에서 사입한 상품을 수익원가 탭에 손으로 입력하는 작업을 없앤다. 영수증을 촬영하거나 캡처 이미지를 붙여넣으면 시스템이 품목을 읽어 입고 초안을 만들고, 사람은 검토·확정만 한다.

**자동화하지 않는 것은 확정 판단이다.** OCR이 만든 초안은 항상 사람이 승인해야 `cost_entries`에 들어간다. 이 기능이 만들어내는 값은 마진 계산의 원장이 되므로, 틀린 수치가 조용히 퍼지는 경로를 구조적으로 차단한다.

## 2. 배경

### 2-1. 기존 시스템

| 항목 | 현황 |
|---|---|
| 입고 저장소 | `cost_entries` — `product_cost_id`(FK) + `received_at` / `quantity` / `unit_cost` / `unit_shipping_fee` / `unit_rg_shipping_fee` / `variant_name` |
| 소분 입고 | 같은 테이블. `purchase_quantity`(사입 총량) + `subdivision_unit`(소분 단위). `unit_cost`에 **총 구매가**를 넣으면 서버가 `calculateSubdivision()`으로 팩당 단가와 이월을 계산 |
| 입고 API | `POST /api/cost-management/products/[id]/entries` — 소분 분기·이월 갱신까지 완비 |
| 데스크톱 UI | `src/components/orders/CostEntryDrawer.tsx` (542줄, 1100px 고정폭) |
| 모바일 셸 | `/m/costco` (480px 레이아웃). `MobileBottomSheet` / `MobileEmptyState` / `MobileFilterChipBar` 재사용 가능 |
| Vision LLM | `@anthropic-ai/sdk` (설치·`ANTHROPIC_API_KEY` 설정 완료), `src/lib/ai/claude-vision.ts` — `resizeForClaude`, `AllowedMimeType` |
| CLOVA OCR | `src/lib/ai/clova-ocr.ts`가 있으나 **환경변수 미설정으로 비활성** 상태. v1에서는 쓰지 않는다 (§5-1) |
| Storage | `src/lib/supabase/server.ts`에 업로드 헬퍼 존재 (**공개 URL 반환 — 영수증에는 부적합**) |

### 2-2. 사용 시나리오

1. **매장에서 촬영** — 계산 직후 주차장에서 한 손으로. 업로드만 하고 그 자리를 뜬다.
2. **캡처 붙여넣기** — 카톡·문자·온라인 주문내역 캡처를 클립보드에서 붙여넣는다.
3. **나중에 확정** — 폰에서 바로 하거나, 집에 와서 데스크톱 수익원가 탭에서 한다.

### 2-3. 도메인 사실

| 사실 | 설계에 미치는 영향 |
|---|---|
| **소분이 기본** — 코스트코 대용량 1박스를 사서 N팩으로 나눠 판다 | 입고 대부분이 `subdivision` 모드 |
| **소분 파라미터는 영수증에 없다** — 포장당 개수, 소분 갯수는 어디에도 안 찍힘 | 시스템이 품번별로 **기억**해야 한다. 이것이 매핑 테이블의 존재 이유 |
| **판매용·개인용이 한 영수증에 섞인다** | 품목별로 입고/제외를 골라내는 단계가 필수 |
| **같은 품번이 때에 따라 다르다** — 타올을 팔기도 하고 집에서도 쓴다 | 매핑은 boolean이 아니라 3상태(`ingest`/`skip`/`ask`) |
| **단가 기준은 할인 반영 후 실결제액(VAT 포함)** | 영수증 한 장으로 검증 가능. 역전파 리스크 최소 |
| 한 줄의 수량을 쪼개는 경우는 없다 | 줄 분할 미지원 |

## 3. 아키텍처

### 3-1. 파이프라인

```
[촬영/붙여넣기]  →  [초안 생성]  →  [OCR+검산]  →  [매핑 자동채움]  →  [사람 검토]  →  [입고 확정]
    폰 즉시           서버 저장      백그라운드      costco_item_map     폰 or 데스크톱   cost_entries
```

**촬영과 OCR을 분리한다.** 매장에서 LLM 응답을 기다리게 하지 않는다. 업로드가 끝나는 즉시 "접수됨"으로 화면을 닫고, 분석은 서버가 뒤에서 처리한다. 통신이 끊겨도 이미지만 올라갔으면 초안은 살아 있다.

### 3-2. 확정의 단위는 영수증이 아니라 품목

영수증을 통째로 확정하지 않고 **품목 한 줄씩 독립적으로 확정**한다. 각 줄은 확정되면 자기가 만든 `cost_entries.id`를 기록한다.

1. **부분 실패가 복구 가능하다.** 8개 품목 중 3번째에서 소분 이월 오류가 나도 1·2번은 이미 들어갔고 3번부터 재시도하면 된다.
2. **중복 입고가 구조적으로 막힌다.** `cost_entry_id`가 박힌 줄은 다시 확정되지 않는다. 저장 버튼을 두 번 눌러도 안전하다.
3. **판매용·개인용 혼재가 자연스럽게 처리된다.** 개인용 줄은 `skip`으로 남고, 영수증은 "8줄 중 5줄 확정, 3줄 제외"로 완결된다.

### 3-3. 기존 코드와의 관계

| 대상 | 처리 |
|---|---|
| `POST /api/cost-management/products/[id]/entries` | **그대로 재사용.** 소분 계산·이월 갱신 로직을 복제하지 않는다 |
| `CostEntryDrawer.tsx` | **건드리지 않는다.** 데스크톱 수동 입력은 현행 유지 |
| `/m/costco` | 하단 탭바를 세우고 「영수증」 탭 추가 |
| 수익원가 탭 | 상단에 "미확정 영수증 N건" 배지 추가 |
| `claude-vision.ts` | `resizeForClaude` 재사용. 수정 없음 |
| `supabase/server.ts` | 비공개 버킷 업로드 경로 추가 (기존 헬퍼는 공개 URL 반환) |

검토 UI는 **컴포넌트 하나**로 만들고 모바일/데스크톱이 폭만 다르게 쓴다. 로직이 두 벌이 되면 소분 계산이 두 곳에서 갈라진다.

## 4. 데이터 모델

신규 테이블 3개, 기존 테이블 컬럼 1개 추가.

### 4-1. `receipt_drafts` — 영수증 1장

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid | |
| `image_paths` | text[] | Supabase Storage 경로들 (긴 영수증은 여러 장) |
| `purchased_at` | date | 영수증에 찍힌 구매일 |
| `purchased_time` | time | 결제 시각. **중복 판정에 쓴다** (§7) |
| `register_no` | text | 계산대 번호(`REG:8`). 중복 판정 보조 |
| `store_name` | text | 지점명 |
| `receipt_total` | int | 영수증 하단 **결제 총액** |
| `total_item_count` | int | 영수증의 "총 판매 상품수". **수량 합계이지 줄 수가 아니다** |
| `tax_exempt_total` | int | 면세 |
| `taxable_total` | int | 과세 |

| `status` | text | `draft` / `done` / `discarded` |
| `created_at` / `updated_at` | timestamptz | |

영수증이 자체적으로 들고 있는 합계값들(`receipt_total`, `total_item_count`, 세금 3종)을 **전부 저장한다.** 각각이 독립된 검산의 기준값이 된다 — 저장하지 않으면 나중에 재검증할 수 없다.

### 4-2. `receipt_draft_lines` — 품목 1줄

| 컬럼 | 타입 | 설명 |

| `item_label` | text | 영수증 표기 상품명 |

| `amount` | int | 금액. 할인 줄은 **음수** |
| `is_discount` | boolean | CPN 할인 줄 여부 |

### 4-3. `costco_item_map` — 학습형 매핑

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid | |
| `item_code` | text | `UNIQUE (user_id, item_code)` |
| `item_label` | text | 최근 관측된 표기 |
| `product_cost_id` | uuid FK ON DELETE SET NULL | 연결 대상 |
| `default_decision` | text | `ingest` / `skip` / `ask` |
| `default_entry_type` | text | `normal` / `subdivision` |
| `items_per_box` | int | |
| `subdivision_unit` | int | |
| `times_used` | int | 신뢰도 표시용 |
| `last_seen_at` | timestamptz | |

**이 테이블이 자산이다.** 코스트코 재구매는 같은 품번의 반복이라, 서너 번 장을 보고 나면 대부분의 품목이 자동으로 채워진다.

`default_decision`을 3상태로 둔 이유: 같은 품번이 어떤 날은 판매용, 어떤 날은 개인용일 수 있다. boolean이면 조용히 틀린 쪽으로 흘러간다 — 개인용으로 찍혀 있으면 판매 입고가 누락되고, 판매용으로 찍혀 있으면 집에서 쓴 게 원가로 들어간다. 둘 다 나중에 발견하기 어렵다. `ask`는 "매번 물어봐"를 뜻한다.

### 4-4. `cost_entries` 컬럼 추가

```sql
ALTER TABLE cost_entries
  ADD COLUMN IF NOT EXISTS source_receipt_line_id uuid
    REFERENCES receipt_draft_lines(id) ON DELETE SET NULL;
```

입고 한 건이 어느 영수증 몇 번째 줄에서 왔는지 되짚을 수 있게 한다. "이 원가 어디서 나온 거지"를 물었을 때 영수증 사진까지 한 번에 열린다.

**`ON DELETE SET NULL`이어야 한다.** `CASCADE`는 영수증 초안을 지웠을 때 실제 회계 데이터인 `cost_entries`까지 지운다. 반대로 FK를 아예 안 걸면 초안 삭제 후 dangling 포인터가 남아 조회가 조용히 실패하고, 화면이 "출처 삭제됨"이라고 말할 수도 없다.

> **`receipt_draft_lines.cost_entry_id`는 반대로 FK를 걸지 않는다.** 대칭처럼 보이지만 판단이 다르다. 확정을 취소해 `cost_entries` 행을 지웠을 때 `ON DELETE SET NULL`이 걸려 있으면 `cost_entry_id`가 NULL이 되고, 그러면 **"확정한 적 없음"과 구분이 사라진다.** NULL 여부가 §3-2 멱등성 판정의 근거이므로 그 구분이 무너지면 같은 줄이 두 번 확정될 수 있다.

### 4-5. 추가 제약

| 항목 | 내용 |
|---|---|
| RLS | 3테이블 전부 `ENABLE ROW LEVEL SECURITY`, 정책 없음. 서버 API는 owner 연결로 통과하고 Supabase 클라이언트 직접 접근만 차단한다 (`054` negotiation_logs 원칙, `089` daily_expenses와 동일) |
| 양수 CHECK | `quantity` · `items_per_box` · `subdivision_unit` `> 0`, `times_used >= 0`. **`amount`와 `unit_price`에는 걸지 않는다** — 할인 줄이 음수다 |
| `updated_at` 트리거 | `receipt_drafts` · `costco_item_map`에 `handle_updated_at()` 연결. 없으면 두 컬럼이 영원히 `created_at`과 같은 값으로 남는다 |

**보류한 제약 하나를 기록해둔다.** `is_discount = true`면 `amount < 0`이라는 CHECK를 검토했으나 걸지 않았다 — 실물에서 확인한 할인 형태가 아직 한 종류뿐이라(수량 동일·단가 차감형) 하드 제약이 이르다. Open Question 2번과 같은 사안이다.

## 5. OCR 파이프라인

### 5-1. 방식 — Vision LLM 단독

영수증 이미지를 `claude-opus-5`에 직접 넣고 구조화된 JSON을 받는다.

```
이미지 → [전처리] → [Vision LLM] → JSON → [검산]
```

**CLOVA OCR을 쓰지 않는 이유.** 초기 검토에서는 CLOVA(숫자 정확도)와 LLM(구조 해석)을 결합하는 안을 고려했으나, 비용을 실제로 계산하고 선결 조건을 따져본 결과 근거가 약했다.

| | 하이브리드 | Vision 단독 |
|---|---|---|
| 월 비용 (8장 기준) | 약 376원 (추정) | **약 540원 (실측)** |
| 숫자 오독 위험 | 낮음 | 보통 — 단 **§5-6 검산이 1차로 잡는다** |
| 선결 조건 | CLOVA 키 발급 + 래퍼 좌표 확장 + 버킷 | 버킷만 |
| 구현 항목 | 9개 | 8개 |

월 볼륨이 4~8장(주 1~2회 장보기)이라 **두 방식의 비용 차이는 월 200원 수준**이다. 이 규모에서 비용은 의사결정 변수가 아니다. 반면 선결 조건이 둘 줄어드는 것은 착수 시점을 몇 주 당길 수 있는 실익이다.

숫자 오독은 합계 검산이 잡는다. 그리고 월 8장이면 사람이 전부 눈으로 훑기 때문에, 검산을 통과한 오독이 남아도 발견될 여지가 크다.

**나중에 갈아끼울 수 있다.** OCR 단계는 검산·매핑 로직과 분리돼 있으므로, 실측에서 검산 실패율이 높으면 그때 CLOVA를 앞단에 끼운다. 검산 테스트는 그대로 통과 기준으로 남는다.

> 참고 — CLOVA General OCR은 월 5,000건 무료, 이후 1,000건당 약 1,500원(검색 기준, 공식 요금표 미대조). 이 볼륨에서는 사실상 0원이지만, 위 표대로 그 차이가 결정을 바꾸지 못한다.

### 5-2. 선결 조건

| 항목 | 현황 | 필요 조치 |
|---|---|---|
| 비공개 Storage 버킷 | 기존 헬퍼(`supabase/server.ts`)는 `getPublicUrl` 반환 | 영수증 전용 비공개 버킷 + 서명 URL 경로 신설 |

`ANTHROPIC_API_KEY`는 `.env.local`에 이미 설정돼 있어 별도 발급이 필요 없다.

### 5-3. 전처리

| 항목 | 처리 |
|---|---|
| HEIC (iOS) | `sharp`로 JPEG 변환 (설치됨) |
| 방향 | `sharp().rotate()` — EXIF 기준 자동 회전. **인위적 회전은 하지 않는다**: 실측에서 영수증이 프레임 안에 가로로 누운 사진도 전 줄 정확히 읽혔다 |
| 해상도 | 긴 변 **2,576px** 이하로 리사이즈 — `claude-opus-5` 고해상도 상한. **더 줄이지 않는다**: 영수증은 글자가 조밀해 해상도를 낮추면 숫자 오독이 늘고, 그것이 Vision 단독의 유일한 약점이다 |
| 긴 영수증 | 한 초안에 이미지 여러 장. 결과를 이어붙여 하나의 `lines` 배열로 |

### 5-4. Vision 추출 계약

`zod`(설치됨) + structured outputs(`output_config.format`)로 스키마를 강제한다.

```
{
  store_name:       string | null,
  purchased_at:     "YYYY-MM-DD" | null,   // 영수증은 MM/DD/YYYY로 찍힌다
  purchased_time:   "HH:MM" | null,
  register_no:      string | null,          // "REG:8"의 8
  receipt_total:    integer | null,         // 합계 (VAT 포함)
  total_item_count: integer | null,         // 총 판매 상품수 = 수량 합계
  tax_exempt_total: integer | null,         // 면세
  taxable_total:    integer | null,         // 과세
  vat:              integer | null,         // 부가세
  lines: [{
    line_no:     integer,
    item_code:   string | null,   // 코스트코 품번
    item_label:  string,
    quantity:    number,
    unit_price:  integer | null,  // 줄 검산의 근거
    amount:      integer,         // 할인 줄은 음수
    is_discount: boolean,
    tax_type:    "taxable" | "exempt" | "unknown"
  }]
}
```

nullable 필드는 `type: ["string","null"]`이 아니라 **`anyOf: [{type:"string"},{type:"null"}]`** 로 쓴다 — structured outputs가 타입 배열을 지원하지 않는다. 모든 필드를 `required`에 넣고 `additionalProperties: false`를 준다.

**호출 설정**

| 항목 | 값 |
|---|---|
| 모델 | `claude-opus-5` |
| 출력 강제 | `output_config.format` (json_schema) — `zodOutputFormat` 헬퍼 사용 |
| effort | `high` (기본값). **낮추지 않는다** — 조밀한 숫자를 정확히 읽는 것이 이 호출의 전부이고, 볼륨이 월 8장이라 절감액이 무의미하다 |
| thinking | 기본값(생략 시 adaptive) |

> 저장소는 현재 `claude-sonnet-4-6`을 주로 쓴다. 이 작업만 `claude-opus-5`로 잡은 이유는 숫자 오독이 원가를 오염시키기 때문이다. `claude-sonnet-5`와의 차이는 월 220원 수준이라 정확도를 깎을 이유가 없다.
>
**실측 (2026-08-08, 실제 코스트코 영수증 2장)**

| 영수증 | 이미지 | input | output | 지연 | 비용 |
|---|---|---|---|---|---|
| 3품목 | 1932×2576 | 5,993 | 271 | 11.9s | 약 53원 |
| 13품목 (CPN 2건) | 1932×2576 | 5,993 | 1,022 | 14.2s | 약 80원 |

**장당 평균 약 67원.** 월 8장이면 약 540원. input은 이미지 크기가 같으면 고정이고, output만 품목 수에 비례한다.

**지연 12~14초** — §3-1의 "촬영과 OCR 분리" 설계가 실측으로 정당화됐다. 매장에서 이만큼 기다리게 할 수 없다.

### 5-5. 프롬프트의 단 하나의 원칙

> **읽히지 않으면 `null`. 추측 금지.**

LLM은 애매한 값을 만나면 빈칸으로 두는 대신 그럴듯한 값을 채운다. `null`이 오면 사용자가 그 칸만 채우면 되지만, 틀린 값이 오면 아무도 모른 채 원가로 들어간다.

**실제 영수증에서 확인된 구조** (2026-08-08 샘플 2장). 아래를 프롬프트에 명시하면 두 장 모두 전 줄 정확 추출됐다.

- 품목은 **두 줄**로 찍힌다 — 윗줄에 상품명, 아랫줄에 `품번 수량x 단가 금액 과세마커`
- 과세 상품은 금액 뒤에 `T`가 붙고, 면세 상품은 붙지 않는다
- 쿠폰 할인은 `CPN` 마커 뒤 **별도 줄**로 찍히며 **자체 품번과 자체 상품명을 갖는다**. `is_discount=true`, `amount`를 음수로 해서 **독립 줄로 담는다** — 원 품목에 합치지 않는다 (이유는 §5-7)
- `상품수 소계`, `PRESCAN 상품 시작/종료` 같은 구분선은 품목이 아니다
- **같은 품번이 한 영수증에 여러 줄 나온다.** 합치지 말고 나온 순서대로 각각 담는다
- 봉투값·멤버십 등 품번 없는 줄은 `item_code: null`로 담는다 (버리면 합계가 안 맞음)
- **회원번호와 카드번호는 추출하지 않는다** — 스키마에 담을 필드 자체를 두지 않는다

### 5-6. 검산

코스트코 영수증은 **자체 검산 장치를 네 개** 들고 있다. 전부 쓴다.

| # | 검산 | 잡아내는 것 | 실증 |
|---|---|---|---|
| 1 | `Σ amount == receipt_total` | 줄 누락, 금액 오독 | 두 장 ✓ |
| 2 | **`quantity × unit_price == \|amount\|`** (줄 단위) | **틀린 줄을 특정** | 전 16줄 ✓ |
| 3 | `Σ quantity` (할인 줄 제외) `== total_item_count` | 줄 누락, 수량 오독 | 19 ✓ / 29 ✓ |
| 4 | `tax_exempt_total + taxable_total + vat == receipt_total`, 그리고 `Σ amount(exempt) == tax_exempt_total` | 과세 구분 오독 | 26,280 ✓ |

**2번이 나머지와 질적으로 다르다.** 1·3·4는 "어딘가 틀렸다"까지만 알려주지만, 2번은 **어느 줄이 틀렸는지 짚어준다.** 사용자가 영수증 전체를 다시 훑는 대신 그 줄만 고치면 된다.

#### 판정과 화면

| 조건 | `verify_status` | 화면 |
|---|---|---|
| 4종 모두 통과 | `matched` | 🟢 검산 통과 |
| 하나라도 불일치 | `mismatch` | 🟡 어떤 검산이 깨졌는지 + **줄 검산이면 해당 줄을 붉게 표시** |
| 기준값이 null | `unreadable` | ⚪ 읽지 못한 항목 표시 |

개별 결과는 `verify_detail` jsonb에 남겨 나중에 재검증할 수 있게 한다.

**불일치라도 확정을 막지 않는다.** 봉투값 하나 때문에 기능 전체가 잠기면 아무도 안 쓴다. 대신 확정 버튼 위에 무엇이 안 맞는지 크게 띄우고 사용자가 "확인했음"을 한 번 누르게 한다. 막는 게 아니라 **보이게 하는 것**이 목적이다.

### 5-7. 할인 귀속 — 추출과 해석을 분리한다

CPN 할인 줄은 **추출 단계에서는 독립 줄로 두고, 검토 단계에서 원 품목에 귀속시킨다.**

추출 단계에서 합치지 않는 이유는 할인 줄이 원 품목과 **다른 품번, 다른 상품명**을 갖기 때문이다. 귀속 근거가 "바로 앞 줄"이라는 위치뿐이라, 모델이 합치게 하면 틀린 귀속이 조용히 섞인다. 게다가 독립 줄로 두면 §5-6의 1번 검산이 단순 합으로 성립한다(실증됨).

**하지만 귀속하지 않으면 원가가 할인 전 금액이 된다.** 사용자가 정한 기준은 "할인 반영 후 실결제액"이므로, 검토 단계에서 반드시 반영해야 한다.

```
      KS라운드티 6매 L
7771922  5x  32,990  164,950 T     ← 원 품목
CPN
      KS라운드티IRC
16612    5x   7,000  -35,000        ← 할인 (수량 동일, 단가 차감형)
```

| 단계 | 처리 |
|---|---|
| 추출 | 두 줄 그대로. 할인 줄은 `is_discount=true`, `amount=-35,000` |
| 자동 귀속 제안 | `is_discount` 줄을 **직전 비할인 줄**에 연결 (`applies_to_line_id`). 수량이 같으면 신뢰도 높음 |
| 검토 화면 | 원 품목 카드에 `164,950 − 35,000 = 129,950` 표시. 귀속을 해제·변경할 수 있게 |
| 확정 | 일반 입고 `unit_cost = (164,950 − 35,000) / 5 = 25,990`<br>소분 입고 `unit_cost`(총 구매가) `= 129,950` |

샘플에서 `32,990 − 7,000 = 25,990`으로 단가끼리도 정확히 떨어졌다. 다만 **수량이 다른 할인 형태를 아직 못 봤으므로**, 확정 계산은 단가 차감이 아니라 **금액 합산** 기준으로 한다 — 어떤 할인 형태가 와도 성립한다.

할인 줄 자체는 `cost_entries`를 만들지 않는다. `decision`은 항상 `skip`이고, 값은 귀속된 품목의 `unit_cost`에만 반영된다.

### 6-3-1. `포장당 개수` 자동 제안

**상품명에 포장 수량이 들어 있는 경우가 많다.** 샘플에서 확인된 것:

| 상품명 | 추출 |
|---|---|
| `KS노랑타월36CT` | 36 |
| `KS라운드티6매 L` | 6 |
| `동물복지란60개` | 60 |
| `소금버터빵 6CT` | 6 |

`(\d+)\s*(CT|개|매|입|P|PK)` 정도의 패턴으로 뽑아 **`포장당 개수` 입력란의 초깃값으로 채운다.** 사용자는 확인만 하면 되므로 첫 매핑 등록 부담이 크게 준다.

**어디까지나 제안이다.** 자동으로 확정하지 않고 입력란에 미리 채워두기만 한다 — `36CT`가 포장 단위가 아닐 수도 있고, 판매 소분 단위와도 다르다.

## 7. 엣지 케이스

| 상황 | 처리 |
|---|---|
| 같은 영수증 두 번 촬영 | `purchased_at` + `purchased_time` + `register_no` + `receipt_total`이 모두 같을 때만 "중복 의심" 배지. **자동 병합 안 함**<br>날짜+금액만으로 판정하면 오탐이 난다 — 샘플 2장이 실제로 **같은 날 같은 지점**(2026-08-08 양재점)에서 나왔다. 시각(09:05 / 10:16)과 계산대(REG 8 / REG 17)까지 봐야 구분된다 |
| OCR 실패 | `ocr_status='failed'`. 초안과 이미지는 남기고 재분석/재촬영 버튼 제공 |
| 품번 없는 줄 (봉투) | `item_code=null` → 기본 `skip`. 단 금액은 검산 합계에 **포함** |
| 연결 상품이 삭제됨 | FK `ON DELETE SET NULL`. "상품 없음 — 다시 지정" 표시 |
| 한 영수증에 같은 상품 두 줄 | 소분 이월이 순서에 의존하므로 **`line_no` 오름차순 직렬 확정**. 병렬 처리 금지 |
| 확정 취소 | v1에 별도 UI 없음. 데스크톱 드로어에서 입고 건을 삭제하고, 줄은 `cost_entry_id`가 가리키는 행이 없으면 "삭제됨" 표시 |
| 긴 영수증 | 한 초안에 이미지 여러 장 |
| 통신 끊김 | 업로드 실패 시 재시도 버튼. 오프라인 큐는 v1 제외 |

> 🟡 **수용된 위험 (2026-08-08 결정).** 원본 이미지는 공개 버킷에 저장한다. 영수증에는 회원번호와 카드번호 뒷자리가 인쇄되어 있으므로, **URL이 유출되면 그 번호들이 함께 노출된다.** 추출 스키마에서 번호를 빼는 조치는 DB 오염만 막을 뿐 이미지 자체는 보호하지 못한다.
>
> 비공개 버킷 + 서명 URL을 제안했으나 채택되지 않았다 — 저장소에 `createSignedUrl` 사용처가 하나도 없어 전례 없는 인프라이고, 버킷 생성이 수작업이다. 현재 버킷은 하나뿐이고 객체 354개가 전부 공개다.
>
> **완화책은 경로 추측 불가능성 하나뿐이다.** `receipts/{user_id}/{draft_uuid}/{n}.jpg` 형태로 uuid를 경로에 넣는다. URL을 모르면 접근할 수 없지만, 아는 사람은 인증 없이 볼 수 있다. 노출 경로가 생기면(로그·공유·스크린샷) 되돌릴 수 없다.

## 8. 테스트 전략

vitest와 playwright가 이미 설정돼 있어 새 도구는 없다.

| 계층 | 대상 | 방식 |
|---|---|---|
| 순수 함수 | **검산 4종**(§5-6), 할인 귀속(§5-7), 포장 수량 추출(§6-3-1), 매핑 조회 → 초안 자동채움 | vitest. 가장 먼저, 가장 촘촘하게 |
| 추출 파이프라인 | Vision 응답 JSON → 초안 생성 | fixture 기반. 모델 호출 자체는 테스트하지 않음 |
| 확정 멱등성 | 같은 줄 두 번 확정 → `cost_entries`가 하나만 생기는가 | vitest + DB |
| 소분 이월 누적 | 같은 상품 두 줄 순차 확정 → 이월이 맞게 이어지는가 | vitest. **가장 깨지기 쉬운 곳** |
| 화면 흐름 | 업로드 → 검토 → 확정 | playwright e2e |

### 확보된 fixture (2026-08-08)

| 파일 | 내용 | 검증하는 것 |
|---|---|---|
| `IMG_3460` | 3품목, PRESCAN, 총 587,630 | 같은 품번 2줄(693817), PRESCAN 구분선 |
| `IMG_3461` | 13품목 + CPN 2건, 총 724,310 | 할인 귀속, 면세 2건, 상품수 소계 3그룹, 같은 품번 2줄(690437) |

두 장의 **모델 응답 JSON을 그대로 고정**해 골든 파일로 쓴다. 실측에서 검산 4종과 줄 검산 전 16줄이 통과했으므로, 이 값들이 회귀 기준선이 된다.

**앞으로 채워야 할 케이스** — 아직 샘플이 없다: 봉투값 등 품번 없는 줄, 검산이 실제로 깨지는 영수증, 여러 장으로 나눠 찍어야 하는 긴 영수증.

**fixture 영수증은 자산이다.** 코스트코가 레이아웃을 바꾸면 테스트가 먼저 알려준다.

## 9. 범위

### 9-1. 만드는 것

1. 마이그레이션 — 3테이블 + `cost_entries.source_receipt_line_id`
2. 비공개 Storage 버킷 업로드 경로
3. 업로드 API — 이미지 → Storage → 초안 생성 (즉시 반환)
4. Vision 추출 → **검산 4종** → 할인 자동 귀속
5. `costco_item_map` 학습·조회 + 포장 수량 자동 제안
6. 확정 API — 줄 단위, 멱등, `line_no` 직렬, 할인 반영
7. `/m/receipt` 3화면 + 하단 탭바
8. 데스크톱 배지 + 검토 컴포넌트 재사용

### 9-2. 만들지 않는 것

| 제외 | 이유 |
|---|---|
| 줄 수량 분할 | 필요 없다고 확인됨 |
| 개인용 지출 가계부화 | 사업 지출이 아님. `daily_expenses`에 넣으면 원가가 오염된다 |
| 오프라인 큐 | M-3 PWA 영역 |
| 이마트·기타 매장 영수증 | 코스트코 하나로 검증 후 확장 |
| 영수증 검색·통계 | 쓰이는 걸 본 뒤에 |
| **사람 검토 없는 자동 확정** | **절대 만들지 않는다.** 이 기능의 안전장치 전체가 검토 단계에 있다 |

### 9-3. 구현 순서

```
1. 마이그레이션 + 매핑 테이블
2. 검산·매핑 순수 함수 + 테스트          ← 여기서 정확도가 결정된다
3. Vision 추출 파이프라인 (fixture 테스트)
4. 비공개 버킷 + 업로드 → 초안 API
5. 확정 API (멱등 + 직렬)
6. /m/receipt 3화면
7. 데스크톱 연동
```

**2번을 3번보다 먼저 하는 것은 의도적이다.** 검산 로직이 테스트로 굳어 있으면 OCR을 어떤 방식으로 바꾸든 정확도 기준이 흔들리지 않는다.

## Open Questions

1. **검산 실패율의 허용선** — 샘플 2장은 전부 통과했다. 표본이 작으므로 운영하며 `mismatch` 비율을 계속 본다. **몇 %부터 CLOVA 도입(§5-1)을 검토할지는 아직 정하지 않았다.**
2. **수량이 다른 할인 형태** — 샘플의 CPN은 원 품목과 수량이 같았다(5x ↔ 5x). 수량이 다르거나 정액 할인인 형태를 아직 못 봤다. §5-7의 확정 계산을 금액 합산 기준으로 잡아 어떤 형태든 성립하게 했지만, 자동 귀속 제안의 신뢰도 판정은 실물을 더 봐야 한다.
3. **매장 통신 환경** — 코스트코 매장 안 셀룰러가 업로드를 감당하는가? 실패율이 높으면 오프라인 큐를 v1으로 당겨야 한다.
4. **원본 이미지 보관 기간** — 무기한 보관인가, 확정 후 N개월인가? 용량은 작지만 개인정보 관점에서 정책이 필요하다.
