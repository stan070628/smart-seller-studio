# 쿠팡 실판가 수동 입력 설계

**작성:** 2026-07-31
**선행:** `docs/superpowers/plans/2026-07-31-sourcing-discovery-phase1.md` (1단계 구현 완료, PR #12 병합)

---

## 왜 필요한가

**네이버 쇼핑 검색 API가 2026-07-31자로 영구 종료됐다.** 유예 없음, 대체 API 없음, 기존 키도 호출 불가 (개발자센터 공지 32530).

1단계에서 만든 판정 로직은 쿠팡 p25를 기준으로 삼는데, 그 값을 만드는 `estimateCoupangPrice`가 이 API에 의존한다. 확인한 증거:

| 검증 | 결과 |
|---|---|
| `GET /v1/search/shop.json` | HTTP 404 · `SE05` (존재하지 않는 검색 api) |
| `GET /v1/search/blog.json` (같은 키) | HTTP 200 — 자격증명은 정상, 쇼핑만 폐기 |
| `sourcing_shortlist` 중 `coupang_p25 IS NOT NULL` | **0건 — 한 번도 채워진 적 없음** |

즉 **모든 후보가 `unknown` 판정**이 되고, `keyword-pipeline`의 자동 적재 조건(`verdict === 'pass'`)이 영원히 발동하지 않아 **소싱리스트에 아무것도 쌓이지 않는다.**

### 다만 판정의 어려운 절반은 살아 있다

`breakEvenPrice(실효원가, 사이즈)`는 순수 함수다. 1단계에서 바로잡은 수수료 11.88%·물류비 실효원가·관세 과세운임이 전부 여기로 들어가고, 외부 API를 쓰지 않는다.

**없어진 것은 "쿠팡에서 실제로 얼마에 팔리나" 한 값뿐이며, 그것은 사람이 검색창에서 10초면 확인한다.** 이 설계는 그 한 칸만 사람에게 넘긴다.

## 결정 사항

| # | 결정 | 근거 |
|---|---|---|
| 1 | 판단 작업은 **발굴 탭 한 화면**에서 끝낸다 | 실행한 화면에 결과가 안 보여 탭 3개를 오가야 했다 |
| 2 | 실행 중에는 **자동 폴링** — 끝난 키워드부터 표시 | 키워드당 약 21초, 10개면 3분 반. 다 끝날 때까지 빈 화면은 못 쓴다 |
| 3 | 쿠팡가 **없이도 담을 수 있다** | 소싱리스트를 "보고 있는 후보함"으로 쓴다. 쿠팡 검색은 나중에 몰아서 |
| 4 | 발굴 탭은 **10개·극소형 고정 가정**, 조정은 소싱리스트에서 | 1차 선별 속도 우선. 후보당 입력칸 3개는 화면을 못 쓰게 만든다 |

결정 3의 대가로 **쿠팡가 입력칸이 발굴 탭과 소싱리스트 두 곳에 필요하다.** 받아들인다.

## 흐름

```
발굴 탭
  시드 선택 → [분석]  ────────────→  POST /api/sourcing/agent/run
                                        └ createRequest 선행 → requestIds 응답
                                        └ after() 백그라운드 실행
  ⏳ 2/3 완료         ←── 폴링 ────   GET /api/sourcing/agent/run/status?ids=…

  ─ 후보 ──────────────────────────
  ℹ 10개 사입 · 극소형 기준
  캠핑 버너 받침대 스탠드   [도매꾹 ↗]
    도매가 7,650 · 배송비 300 · 실효원가 7,950 · 손익분기 16,945
    쿠팡 실판가 [        ] → 입력 즉시 통과/미달
    [소싱리스트에 담기]
           ↓
소싱리스트
  쿠팡가 입력칸 (발굴에서 비워뒀으면 여기서)
  수량·사이즈 조정 → 손익분기 재계산
```

## 구성 요소

### 1. 폴링이 "이번 실행분"만 보게 한다

지금은 `after()` 안에서 `createRequest`가 요청 행을 만들어 **라우트가 ID를 모른다.** 그래서 폴링이 남의 실행과 섞인다.

**라우트가 `createRequest`를 먼저 동기로 호출해 ID를 확보하고 응답에 담은 뒤, `after()`에서 그 ID로 이어간다.** `runKeywordPipeline`에 `requestId` 인자를 추가한다. 마이그레이션이 필요 없다.

```
POST /api/sourcing/agent/run
  → { success: true, data: { runs: [{ keyword, requestId }] } }

GET /api/sourcing/agent/run/status?ids=12,13,14
  → { success: true, data: { runs: [{ requestId, keyword, status, results[] }] } }
```

`status`는 `keyword_sourcing_requests.status`(`pending`/`done`/`error`)를 그대로 쓴다.

### 2. 판정 계산 위치

`breakEvenPrice`·`marginOf`는 순수 함수라 **브라우저에서 그대로 쓴다.** 타이핑하는 즉시 통과/미달이 바뀐다.

**저장할 때는 서버가 다시 계산한다.** 클라이언트 계산값을 신뢰 경계 너머로 그대로 받지 않는다.

### 3. 자동 적재 블록 제거

`keyword-pipeline.ts`의 `if (v.verdict === 'pass')` 블록은 p25가 영원히 null이라 절대 발동하지 않는다. 죽은 코드로 남기면 다음 사람이 "왜 안 쌓이지"를 다시 판다. **제거하고, 담기는 사용자가 명시적으로 한다.**

### 4. 쿠팡가 저장

`PATCH /api/sourcing/shortlist/[itemNo]`가 현재 허용하는 필드는 `memo`·`logisticsSize`·`orderQty`·`isArchived`뿐이다. **`coupangP25`를 추가하고, 입력 시 서버가 판정을 재계산해 `verdict`·`margin`·`margin_rate`를 갱신한다.**

담기(`POST /api/sourcing/shortlist`)는 기존 경로를 재사용하되, 발굴 탭에서 쿠팡가를 이미 넣었으면 함께 전달한다.

### 5. 죽은 자동 조회가 수동 입력을 덮지 않게 한다

`shortlist-verify`의 `verifyOne`은 `estimateCoupangPrice`를 불러 `unknown`을 쓴다. **시세 조회를 떼어내고, 도매꾹 재고·가격·판매종료 갱신만 남긴다.** 수동 입력한 `coupang_p25`는 절대 건드리지 않는다.

`shortlist-verify` 크론(매일 01:00 KST)은 그대로 유지한다 — 상품이 품절되거나 가격이 오르면 알아야 한다.

> 1단계에서 `verified_at`을 `NULL`로 남기도록 고친 것과 같은 부류의 문제다. 자동 기계가 사람이 채운 값을 덮으면 안 된다.

## 화면

목업: 대화 중 공유한 아티팩트. 실제 `coupang-price.ts` 산식으로 동작한다.

- **가정을 화면에 적는다** — "10개 사입 · 극소형 기준". 1단계에서 이 가정이 안 보여 행 내부가 모순되는 문제가 있었다.
- **미달은 회색으로 낸다.** 빨강은 강조색(쿠팡)이 이미 쓰고, 무엇보다 미달은 흔한 정상 결과다. 후보 5개 중 4개가 미달인 게 보통인데 매번 빨간불이 켜지면 경고가 무뎌진다.
- **미달 사유를 구분해 보여준다** — `1만원 하한 미만`과 `손익분기 N원 부족`은 다른 이야기다.
- 후보당 숫자는 넷(도매가·배송비·실효원가·손익분기). 근거를 추적할 수 있는 최소 단위다.

### 반복 작업을 줄이는 두 가지

한 후보를 판단하는 일을 쪼개면 이렇다.

```
1. 상품명 복사        ← 마우스
2. 쿠팡 탭으로 전환    ← 손
3. 붙여넣고 검색       ← 손
4. 가격 읽기          ← 눈
5. 돌아와서 입력       ← 손
```

**타이핑(5)이 가장 싼 단계다.** 비싼 것은 1~3이므로 거기를 없앤다.

**쿠팡 검색 링크.** 후보마다 `쿠팡에서 검색 ↗`을 단다. 클릭 한 번에 새 탭에서 결과가 이미 떠 있어 1~3이 통째로 사라진다.

```
https://www.coupang.com/np/search?q={검색어}
```

검색어에 **도매꾹 원제목을 그대로 쓰지 않는다.** 원제목에는 판매자명·부속 표현이 섞여 있어(`캠핑 접이식 버너 그리들 초경량 스테인리스 받침대 가방세트 해피포레`) 쿠팡에서 결과가 안 나온다. 이미 있는 `buildSearchQueries(title)`(`coupang-price.ts:102`)의 **첫 번째 결과**를 쓴다 — 위 예시에서 `캠핑 접이식 버너 그리들`이 나온다. 네이버용으로 만든 정규화지만 목적(노이즈 제거)이 같아 그대로 재사용한다.

**Enter로 다음 칸.** 가격 입력 후 Enter를 누르면 다음 후보의 입력칸으로 이동한다. 마지막 칸에서는 이동하지 않는다.

두 가지를 합치면 반복이 `클릭 → 읽기 → 입력 → Enter`로 줄어든다.

## 오류 처리

| 상황 | 동작 |
|---|---|
| 폴링 요청 실패 | 진행 표시 옆에 사유를 띄우고 폴링을 멈춘다. 재시도 버튼을 준다. 조용히 멈추지 않는다 |
| 특정 키워드 `status='error'` | 그 키워드 블록에 사유를 표시하고 나머지는 계속 진행 |
| 폴링이 오래 걸림 | **마지막으로 상태가 바뀐 시점**부터 3분간 변화가 없으면 중단하고 "아직 진행 중일 수 있습니다 — 새로고침" 안내. 실행 시작 기준이 아니다 — 키워드 10개면 정상 실행도 3분 반이 걸린다 |
| 담기 실패 | 버튼을 원복하고 사유를 표시. 담긴 것처럼 보이게 두지 않는다 |
| 쿠팡가 입력값이 비정상 | 음수·비정수·1,000만원 초과는 서버에서 400 |

`after()`는 완료 신호를 주지 않으므로, 폴링 종료 조건은 **모든 `requestId`가 `done` 또는 `error`** 다.

## 테스트

| 대상 | 확인 |
|---|---|
| `evaluateCandidate` | 기존 5건 그대로 — 회귀 방어선 |
| `PATCH`의 `coupangP25` | 음수·비정수·범위 초과 400, 정상값이면 `verdict`·`margin_rate` 재계산 |
| **`verifyOne`이 수동 p25를 보존하는가** | 1단계에서 배운 교훈이라 반드시 고정 |
| 상태 조회 API | 요청한 `ids`만 반환하고 다른 실행이 섞이지 않는가 |
| `runKeywordPipeline` | `requestId`를 받으면 새로 만들지 않고 그것을 쓰는가 |

`DiscoveryTab`은 형제 탭에 렌더 테스트 하네스가 없다(`sourcing-dashboard.test.ts`는 소스를 문자열로 파싱한다). `npm run build`로 검증한다.

## 이 설계에서 제외한 것

| 항목 | 이유 |
|---|---|
| 자동 시세 조회 복구 | 쿠팡 파트너스 API가 유일한 현실적 경로인데 계정에 접근 권한이 없다 |
| 발굴 탭에서 수량·사이즈 조정 | 결정 4. 후보당 입력칸 3개는 1차 선별을 방해한다 |
| 쿠팡가 일괄 입력·붙여넣기 | **병목이 타이핑이 아니라 쿠팡 검색 도달이다.** 검색 링크와 Enter 이동으로 그쪽을 없앴다. 여러 줄 붙여넣기는 순서가 어긋나면 조용히 틀린 값이 들어가는 실패 모드가 있고(후보 정렬·담기로 순서가 밀린다), 이름·가격 쌍 붙여넣기는 그 텍스트를 사람이 만들어야 해 한 줄씩 치는 것과 큰 차이가 없다. 실제로 써 보고 그래도 답답하면 그때 넣는다 — 그때는 어떤 형태가 필요한지도 알게 된다 |
| 코스트코 최저가 비교 복구 | 같은 API에 의존한다. 별건 |
| `isViable` 기준 불일치 | 1단계 계획서에 기록된 별건 |

## 열린 질문

**손익분기가가 실제 감각과 맞는가.** 도매가 7,650원짜리의 손익분기가 16,945원(2.2배)으로 나온다. 수수료 11.88% + 물류비 1,898원 + 마진율 30% + 물류비 1.5배 조건이 겹친 결과다. 계산은 맞지만 `TARGET_MARGIN_RATE`(0.3)와 `MARGIN_TO_LOGISTICS`(1.5)가 이 사업에 맞는 값인지는 실제 매입 몇 건을 돌려봐야 안다. 이 설계의 범위 밖이지만, 첫 사용에서 가장 먼저 부딪칠 지점이다.
