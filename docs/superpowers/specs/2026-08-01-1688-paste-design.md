# 1688 붙여넣기로 두 공급처 원가 비교 설계

**작성:** 2026-08-01
**선행:** `docs/superpowers/specs/2026-07-31-manual-coupang-price-design.md` (쿠팡 실판가 수동 입력, 구현 완료)

---

## 무엇을 만드나

소싱리스트 항목에 **1688 결제 확인 화면을 붙여넣으면** 개당 원가가 계산되어 저장되고, 도매꾹 원가와 나란히 비교된다.

같은 상품이라도 공급처에 따라 판정이 갈린다. 실제 예시:

```
실리콘 필통              쿠팡 실판가 9,000원
─────────────────────────────────────────
도매꾹  원가 3,600  손익분기 9,471   ❌ 미달 — 471원 부족
1688   원가 2,680  손익분기 8,427   ✅ 통과 — 개당 3,353원 · 37.3%
```

1688 원가 2,680원은 실측이다 — 결제 확인 화면 ₩3,867 ÷ 2개 = 개당 1,934원에 국제배송비 322원, 관세 8%, 부가세를 얹은 값이다. 도매꾹 3,600원은 같은 상품을 국내에서 뗐다고 가정한 값이다.

도매꾹으로는 471원이 모자라 버릴 상품이 1688로는 37.3% 마진이 난다. **그 사실이 보이지 않으면 팔 수 있는 상품을 놓친다.**

---

## 화면 선택 — 왜 결제 확인 화면인가

1688에는 가격을 볼 수 있는 화면이 셋 있고, 셋 다 다르다. 실제 화면을 확인해 비교했다.

| 화면 | 개당가가 확정되나 | 아직 안 샀나 | 원화 |
|---|---|---|---|
| 장바구니 | ❌ 체크할 때마다 변동 | ✅ | ❌ |
| **결제 확인** | ✅ | ✅ | ✅ |
| 주문 내역 | ✅ | ❌ 결제 후 | ✅ |

**장바구니를 쓸 수 없는 이유.** 한 줄에 가격이 넷이고(`5.63` 담을 때 · `4.50` 현재가 · `券后价 3.50` 쿠폰 후 · `比加购降2.13元`), 게다가 **품목을 체크하면 값이 바뀐다.** 실측에서 `3.50 → 4.00`으로 올랐다. 상단 배너의 `新人单笔订单满4元, 减1元`(4위안 이상 주문 시 1위안 할인)이 주문 단위 할인이라 품목별로 분배되기 때문이다:

```
4.50 × 2개 = 9.00 − 1.00(주문 할인) = 8.00 ÷ 2개 = 개당 4.00
```

**개당 단가라는 것이 주문 구성이 확정되기 전에는 존재하지 않는다.** 파서가 한 줄만 보고 "이게 단가다"라고 뽑으면 틀린다.

**주문 내역을 쓸 수 없는 이유.** 결제 *이후*에만 보인다. 살지 말지 판단하는 시점에는 없다.

**결제 확인 화면만 "값이 확정됨"과 "아직 안 샀음"을 동시에 만족한다.**

## 파싱

### 뽑는 값

**우측 `价格明细` 블록만 읽는다.** 판매자별 `店铺明细`는 무시한다 — 판매자가 몇이든 전체 합계는 `价格明细` 한 곳에만 있다.

```
价格明细  商品总计 N种M件 · [已减] · 상품총계 · 总运费 · [店铺优惠] · 合计(¥) · KRW(₩)
파생     실효환율 = ₩合计 ÷ ¥合计
         개당 평균가 = ₩合计 ÷ M
```

품목별 금액(`小计`)은 **읽지 않는다.** 계산에 쓰는 값은 `合计`와 수량 `M`뿐이고, 품목 블록은 옵션명·배송예정일·`券后` 라벨이 뒤섞여 문서에서 가장 불안정한 구간이다.

### 원문은 금액이 줄 단위로 쪼개져 온다

2026-08-01 실제 복사 텍스트에서 확인했다. 1688은 금액의 정수부와 소수부를 서로 다른 span으로 렌더링한다.

```
合计
¥
3
.80
```

**`[¥￥]\s*([\d.]+)` 류의 정규식은 여기서 `3`만 잡고 `.80`을 버린다.** `\s*`가 개행을 먹기 때문이다. `\s`를 막으면 `¥ 2`처럼 공백이 낀 정상 케이스가 깨진다. 양립하지 않는다.

또 `商品总计`와 상품총계 사이에 **`已减 ¥0.70`이 끼어들 수 있다.** 그냥 "`商品总计` 뒤 첫 금액"을 집으면 상품총계 자리를 `0.70`이 가로챈다.

### 슬라이스 → 공백 제거 → 라벨 파싱

`价格明细`부터 첫 `₩금액`까지 자른 뒤 공백·개행을 **전부** 지우고 파싱한다. 이 한 수가 네 문제를 동시에 없앤다.

1. 숫자 분할
2. `商品总计`가 `店铺明细`에도 있는 중복 라벨 (판매자 수와 무관해진다)
3. 하단 `立即下单`의 금액·원화 재출현
4. `配送方式 快递 ¥ 3.5` 같은 앞쪽 잡음

정규화 결과 — 실측 원문 2건에서 실제로 얻은 문자열:

```
价格明细商品总计1种1件已减¥0.70¥2.80总运费¥2.00店铺优惠减¥1.00合计¥3.80≈KRW₩840
价格明细商品总计2种2件¥14.00总运费¥3.50合计¥17.50≈KRW₩3,867
```

### 검산은 하나만 건다

```
商品总计 − 店铺优惠 + 总运费 = 合计
```

| 샘플 | 상품총계 − 쿠폰 + 운임 | 合计 | |
|---|---|---|---|
| 豆腐包 (판매자1 · 1件 · 쿠폰O · 已减O) | 2.80 − 1.00 + 2.00 = **3.80** | 3.80 | ✅ |
| 실리콘 필통 (판매자1 · 2件 · 쿠폰X) | 14.00 − 0 + 3.50 = **17.50** | 17.50 | ✅ |

> **초안의 검산 ②갈래를 ①갈래로 줄였다.** 폐기한 쪽은 `Σ小计 + 总运费 = 合计`다. 그 검산은 "쿠폰이 품목에 제대로 분배됐나"를 봤는데, 우리가 쓰는 값은 `合计` 총액이라 품목별 분배는 알 필요가 없다. 검산을 위해서만 가장 취약한 구간을 파싱하는 셈이었다.

**남은 하나가 실패 모드를 다 덮는다.** 이 검산은 `价格明细` 안의 네 값이 서로 아귀가 맞는지를 본다 — 즉 "내가 라벨을 제대로 집었나"를 검증한다. `已减`를 상품총계로 오독하면 `0.70 − 1.00 + 2.00 = 1.70 ≠ 3.80`으로 걸린다. 라벨 오매칭으로 하나라도 `null`이면 그 자리에서 거부한다.

**검산이 어긋나면 저장하지 않고 사람에게 되묻는다.** 화면에 비슷한 숫자가 여럿이므로, 조용히 틀린 값이 원가 모델로 들어가는 것이 가장 위험한 실패다.

### 숫자가 아닌 값을 만난다

`店铺优惠`가 금액이 아니거나 아예 없는 경우가 있다. 실측에서 나온 것:

- 라벨 자체가 없음 — 실리콘 필통 (쿠폰 미적용)
- `包邮` (무료배송) — 스크린샷 샘플의 `店铺优惠`
- `退货包运费` (반품 배송비 포함) — `服务` 행에 나타남

`减¥N` 형태만 가정하면 넘어진다. **파싱에 실패하면 쿠폰을 0으로 두되, 판단은 검산에 맡긴다** — 실제로 쿠폰이 있었는데 못 읽었다면 검산이 어긋나 거부된다.

### 색상 변형은 합친다

실측 주문이 같은 상품의 색상 변형인 경우가 많았다(실리콘 필통 카키/연보라, 슬리퍼 파랑/분홍). 소싱리스트 항목 하나에 대응하므로 **합쳐서 개당 평균가**로 낸다.

중국 내 배송비(`总运费`)는 `合计`에 포함되어 있으므로 개당 평균가에 자동으로 녹아든다.

## 환율

**붙여넣기가 그 주문에 실제 적용된 환율을 들고 온다.** 별도 입력도 API 조회도 필요 없다.

| 출처 | 원/위안 | ECB 대비 |
|---|---|---|
| ECB 기준환율 (2026-07-31) | 213.83 | — |
| 결제 확인 — 豆腐包 (₩840 ÷ ¥3.80) · 원문 확보 | 221.05 | +3.4% |
| 결제 확인 — 실리콘 필통 (₩3,867 ÷ ¥17.50) · 원문 확보 | 220.97 | +3.3% |
| 결제 확인 — 수납袋 (₩4,154 ÷ ¥18.80) · 스크린샷 | 220.96 | +3.3% |
| 결제 확인 — 파우치 (₩1,301 ÷ ¥5.89) · 스크린샷 | 220.88 | +3.3% |
| 주문 내역 (2026-07-29) | 226.69 | +6.0% |
| 주문 내역 (2026-07-27) | 228.90 | +7.0% |
| `DEFAULT_EXCHANGE_RATE_KRW_PER_RMB` | 195.00 | **−8.8%** |

결제 확인 화면 3건이 **220.88~221.00으로 거의 흔들리지 않는다.** 1688이 쓰는 환율이 주문마다 달라지지 않는다는 뜻이라, 붙여넣기가 들고 오는 값을 믿어도 된다. ECB보다 3~7% 높은 것은 결제 스프레드로 보이며, **그것이 실제로 지불하는 환율**이다.

> **별건 — 기본 환율이 8.8% 낮다.** `margin-1688.ts:23`의 `195`는 ECB 기준(213.83)에도 못 미친다. 마진 계산기를 이 값으로 쓰면 1688 원가가 실제보다 싸게 나온다. 이번 범위 밖이지만 고쳐야 한다.

## 저장

**입력값만 저장하고 원가는 볼 때마다 계산한다.** 선행 작업에서 `verified_at` 문제가 "가정에 의존한 파생값을 저장했다가 가정이 바뀌어 행 내부가 모순된" 경우였다.

| 저장하는 값 | 용도 |
|---|---|
| `buy_krw_total` 원화 합계 | 개당 평균가 = 합계 ÷ 수량 |
| `order_qty_1688` 총 수량 | 〃 |
| `intl_ship_per_unit` 개당 국제배송비 | 과세운임 |
| `exchange_rate` 실효환율 | 표시·감사용 |
| `buy_cny_total` 위안 합계 | 표시·감사용 |
| `pasted_at` 붙여넣은 시각 | 값이 언제 기준인지 |

조회할 때마다 이 순서로 계산한다:

```
개당 평균가 = buy_krw_total ÷ order_qty_1688
과세가격    = 개당 평균가 + intl_ship_per_unit
관세·부가세  = calcImportTax(과세가격, 조회 시점 관세율)
실효원가    = 과세가격 + 관세 + 부가세
손익분기가   = breakEvenPrice(실효원가, 물류 사이즈)
```

`exchange_rate`와 `buy_cny_total`은 계산에 쓰이지 않는다. 화면에 `¥17.50 = ₩3,867 (221.0원/위안)`을 함께 보여주고, 나중에 "그때 환율이 얼마였나"를 되짚을 수 있게 남긴다.

환율은 **그때 실제로 적용된 값**이므로 저장한다. 나중에 시장 환율이 변해도 이 주문의 원가는 그때 값이 맞다. 반면 관세율·수수료율처럼 정책이 바뀔 수 있는 값은 저장하지 않고 조회 시점 값을 쓴다.

`sourcing_shortlist`에 1688 관련 컬럼이 없으므로 마이그레이션이 필요하다.

## 국제배송비 — 유일한 수동 입력

붙여넣기가 채우지 못하는 값은 하나뿐이다. 화면의 `总运费`는 **중국 내에서 배대지까지** 가는 비용이고, 배대지에서 한국까지는 별개다.

`intl-shipping.ts`(해운 요율표·부피무게)가 있지만 **무게를 알아야** 쓸 수 있고, 1688 결제 화면에는 무게가 없다. 따라서 개당 배송비를 한 칸 직접 받는다.

**비워두면 경고를 띄운다.** 0으로 두면 1688이 실제보다 싸 보이고, 이는 낙관 방향 오류다 — 통과하면 안 될 후보가 통과한다.

## 판정

**도매꾹과 1688을 각각 낸다.** 원가가 다르니 손익분기도 판정도 다르다.

자동으로 싼 쪽을 고르지 않는 이유: 두 공급처는 **리드타임이 다르다**(국내 2~3일 vs 해운 약 30일 + 통관). 현금 회전과 재고 위험이 달라 단순 비교 대상이 아니다. 숫자는 양쪽 다 보여주고 판단은 사람이 한다.

---

## 화면

목업: 대화 중 공유한 아티팩트. 실제 파서와 원가 산식으로 동작한다.

- 소싱리스트 항목을 펼치면 **도매꾹 / 1688 두 줄**이 나란히 선다. 왼쪽 레일 색으로 구분하고(중립 / 주황), 각 줄에 리드타임을 적는다.
- 1688 줄에 붙여넣기 영역. 파싱하면 **검산 결과가 먼저** 뜨고, 통과해야 원가가 계산된다.
- 미달은 회색으로 낸다. 후보 대부분이 지나가는 정상 결과라 경고색을 쓰지 않는다.

## 오류 처리

| 상황 | 동작 |
|---|---|
| 검산 불일치 | 원가 계산으로 넘기지 않고 사유를 표시. 저장하지 않는다 |
| `合计` 또는 수량을 못 읽음 | "결제 확인 화면 전체를 다시 긁어와 주세요" |
| 원화(`₩`)가 없음 | 장바구니를 붙여넣었을 가능성이 높다 — 화면을 짚어 안내 |
| `价格明细`를 못 찾음 | 화면 우측 가격 영역까지 포함해 긁도록 안내 |
| 국제배송비 미입력 | 저장은 되되 "배송비 미반영 — 실제 원가는 더 높다" 경고 |
| 붙여넣기 저장 실패 | 버튼을 원복하고 사유 표시. 성공한 것처럼 두지 않는다 |

## 테스트

| 대상 | 확인 |
|---|---|
| 파서 | **실측 붙여넣기 원문을 픽스처로 고정한다** (아래) |
| 검산 | 숫자를 하나 틀리게 만든 입력이 **거부되는가** |
| 장바구니 텍스트 | 원화가 없으므로 거부되는가 |
| 개당 평균 | 색상 변형 2개가 합쳐지는가 |
| 원가 | 실효원가·손익분기가 기존 산식과 일치하는가 |
| 저장·조회 | 환율이 보존되고 원가는 재계산되는가 |

**픽스처는 실제 복사 텍스트다.** 배송지 이름·전화번호만 마스킹하고 한 글자도 손대지 않았다 — 1688 화면이 바뀌면 이 픽스처가 먼저 깨져야 한다.

| 픽스처 | 판매자 | 품목 | 배송비 | 쿠폰 | 특이 |
|---|---|---|---|---|---|
| `tofu-pouch.txt` | 1 | 1 | ¥2.00 | 있음 | **`已减 ¥0.70`** 이 상품총계 앞에 낀다 |
| `silicone-pencase.txt` | 1 | 색상 2 | **¥3.50** | **없음** | 천단위 쉼표(`₩3,867`) · 색상 변형 합산 |

두 픽스처가 갈라놓는 것: `已减` 유무, 쿠폰 유무, 배송비 유무, 색상 변형 합산, 쉼표 파싱.

**판매자 2명 케이스는 실제 텍스트가 없다** — 채집 시점에 해당 주문이 장바구니에 없었다. 스크린샷 근거로만 존재한다. 슬라이스가 `店铺明细`를 구조적으로 배제하므로 판매자 수는 원리상 무관하지만, 이 가정을 테스트로 못 박는다: `价格明细` **앞쪽** 금액을 엉뚱한 값으로 바꿔도 결과가 안 변하는지 확인한다.

파서는 순수 함수라 테스트하기 쉽다. UI는 `npm run build`로 검증한다 — 형제 탭에 렌더 하네스가 없다.

## 열린 질문

**붙여넣기 텍스트가 브라우저·복사 방식에 따라 달라질 수 있다.** 설계는 실측 복사 원문 2건과 스크린샷 3건에 기댄다(배송비·쿠폰·`已减`·색상 변형 유무를 덮되, 판매자 복수는 스크린샷 근거뿐이다). 다른 브라우저나 확대/축소 상태에서 형태가 달라지면 파서가 실패할 수 있는데, 그때는 **검산이 막아준다** — 조용히 틀리는 대신 거부한다. 실패 사례가 쌓이면 파서를 넓힌다.
