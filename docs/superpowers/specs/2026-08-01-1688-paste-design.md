# 1688 붙여넣기로 두 공급처 원가 비교 설계

**작성:** 2026-08-01
**선행:** `docs/superpowers/specs/2026-07-31-manual-coupang-price-design.md` (쿠팡 실판가 수동 입력, 구현 완료)

---

## 무엇을 만드나

소싱리스트 항목에 **1688 결제 확인 화면을 붙여넣으면** 개당 원가가 계산되어 저장되고, 도매꾹 원가와 나란히 비교된다.

같은 상품이라도 공급처에 따라 판정이 갈린다. 실제 예시:

```
메쉬 반장갑              쿠팡 실판가 9,900원
─────────────────────────────────────────
도매꾹  원가 3,600  손익분기 9,471   ❌ 미달 — 429원 부족
1688   원가 1,432  손익분기 7,010   ✅ 통과 — 개당 3,731원 · 37.7%
```

도매꾹으로는 429원이 모자라 버릴 상품이 1688로는 37.7% 마진이 난다. **그 사실이 보이지 않으면 팔 수 있는 상품을 놓친다.**

---

## 화면 선택 — 왜 결제 확인 화면인가

1688에는 가격을 볼 수 있는 화면이 셋 있고, 셋 다 다르다. 실제 화면을 확인해 비교했다.

| 화면 | 개당가가 확정되나 | 아직 안 샀나 | 원화 |
|---|---|---|---|
| 장바구니 | ❌ 체크할 때마다 변동 | ✅ | ❌ |
| **결제 확인** | ✅ | ✅ | ✅ |
| 주문 내역 | ✅ | ❌ 결제 후 | ✅ |

**장바구니를 쓸 수 없는 이유.** 한 줄에 가격이 넷이고(`5.63` 담을 때 · `4.50` 현재가 · `券后价 3.50` 쿠폰 후 · `比加购降2.13元`), 게다가 **품목을 체크하면 값이 바뀐다.** 실측에서 `3.50 → 4.00`으로 올랐다. 상단 배너의 `新人单笔订单满4元, 减1元`(4위안 이상 주문 시 1위안 할인)이 주문 단위 할인이라 품목별로 분배되기 때문이다:

```
4.50 × 2개 = 9.00 − 1.00(주문 할인) = 8.00 ÷ 2개 = 개당 4.00
```

**개당 단가라는 것이 주문 구성이 확정되기 전에는 존재하지 않는다.** 파서가 한 줄만 보고 "이게 단가다"라고 뽑으면 틀린다.

**주문 내역을 쓸 수 없는 이유.** 결제 *이후*에만 보인다. 살지 말지 판단하는 시점에는 없다.

**결제 확인 화면만 "값이 확정됨"과 "아직 안 샀음"을 동시에 만족한다.**

## 파싱

### 뽑는 값

**우측 `价格明细` 블록만 읽는다.** 판매자별 `店铺明细`는 무시한다 — 판매자가 몇이든 전체 합계는 `价格明细` 한 곳에만 있고, 실측에서 판매자별 합이 전체와 정확히 일치함을 확인했다.

```
품목별   옵션명(색상·사이즈) · 수량 · 小计
价格明细  商品总计 · 总运费 · 店铺优惠 · 合计(¥) · KRW(₩)
파생     실효환율 = ₩ ÷ ¥合计
         개당 평균가 = ₩合计 ÷ 총 수량
```

**단가가 아니라 `小计`를 읽는다.** `券后价`(쿠폰 후 단가)는 **없는 품목이 있다** — 실측 샘플3의 판매자A는 `单价 ¥2.09` / `小计 ¥2.09`로 쿠폰 줄이 아예 없고, 판매자B는 `券后¥1.80` / `¥3.50`이 있다. `小计`는 쿠폰이 이미 반영된 값이라 유무를 신경 쓸 필요가 없다.

### 검산을 두 갈래로 건다

```
① Σ小计 + 总运费              = 合计
② 商品总计 − 店铺优惠 + 总运费  = 合计
```

실측 3건 전부 통과한다.

| 샘플 | ① Σ小计 + 总运费 | ② 商品总计 − 优惠 + 运费 | 合计 |
|---|---|---|---|
| 모자 (색상 2, 무료배송) | 8.00 + 0.00 = **8.00** | 9.00 − 1.00 + 0.00 = **8.00** | 8.00 |
| 수납袋 (품목 1, 배송비 4) | 14.80 + 4.00 = **18.80** | 17.80 − 3.00 + 4.00 = **18.80** | 18.80 |
| 파우치 (판매자 2) | 3.89 + 2.00 = **5.89** | 4.89 − 1.00 + 2.00 = **5.89** | 5.89 |

> **`+ 总运费`가 빠져 있었다.** 초안은 `Σ小计 = 合计`이었는데, 첫 샘플이 무료배송(`总运费 ¥0.00`)이라 우연히 맞았다. 배송비가 붙는 두 번째 샘플에서 `14.80 ≠ 18.80`으로 깨졌다. **`小计`는 상품 소계이고 배송비는 별도로 얹힌다.**

두 경로가 **독립적으로** 같은 값에 도달한다. 하나만으로는 숫자를 잘못 집어도 모른다.

**검산이 하나라도 어긋나면 저장하지 않고 사람에게 되묻는다.** 화면에 비슷한 숫자가 여럿이므로, 조용히 틀린 값이 원가 모델로 들어가는 것이 가장 위험한 실패다.

### 숫자가 아닌 값을 만난다

`店铺优惠`가 금액이 아닌 경우가 있다. 실측에서 나온 것:

- `包邮` (무료배송) — 샘플3 판매자A의 `店铺优惠`
- `退货包运费` (반품 배송비 포함) — 샘플2의 `服务` 행

`减¥N` 형태만 가정하면 넘어진다. 파싱에 실패한 값은 **0으로 치지 말고** 검산으로 넘겨 판단한다.

### 색상 변형은 합친다

실측 주문이 같은 상품의 색상 변형인 경우가 많았다(슬리퍼 파랑/분홍, 모자 카키/검정). 소싱리스트 항목 하나에 대응하므로 **합쳐서 개당 평균가**로 낸다.

중국 내 배송비(`总运费`)는 `合计`에 포함되어 있으므로 개당 평균가에 자동으로 녹아든다.

## 환율

**붙여넣기가 그 주문에 실제 적용된 환율을 들고 온다.** 별도 입력도 API 조회도 필요 없다.

| 출처 | 원/위안 | ECB 대비 |
|---|---|---|
| ECB 기준환율 (2026-07-31) | 213.83 | — |
| 결제 확인 화면 — 모자 (₩1,768 ÷ ¥8.00) | 221.00 | +3.4% |
| 결제 확인 화면 — 수납袋 (₩4,154 ÷ ¥18.80) | 220.96 | +3.3% |
| 결제 확인 화면 — 파우치 (₩1,301 ÷ ¥5.89) | 220.88 | +3.3% |
| 주문 내역 (2026-07-29) | 226.69 | +6.0% |
| 주문 내역 (2026-07-27) | 228.90 | +7.0% |
| `DEFAULT_EXCHANGE_RATE_KRW_PER_RMB` | 195.00 | **−8.8%** |

결제 확인 화면 3건이 **220.88~221.00으로 거의 흔들리지 않는다.** 1688이 쓰는 환율이 주문마다 달라지지 않는다는 뜻이라, 붙여넣기가 들고 오는 값을 믿어도 된다. ECB보다 3~7% 높은 것은 결제 스프레드로 보이며, **그것이 실제로 지불하는 환율**이다.

> **별건 — 기본 환율이 8.8% 낮다.** `margin-1688.ts:23`의 `195`는 ECB 기준(213.83)에도 못 미친다. 마진 계산기를 이 값으로 쓰면 1688 원가가 실제보다 싸게 나온다. 이번 범위 밖이지만 고쳐야 한다.

## 저장

**입력값만 저장하고 원가는 볼 때마다 계산한다.** 선행 작업에서 `verified_at` 문제가 "가정에 의존한 파생값을 저장했다가 가정이 바뀌어 행 내부가 모순된" 경우였다.

| 저장하는 값 | 용도 |
|---|---|
| `buy_krw_total` 원화 합계 | 개당 평균가 = 합계 ÷ 수량 |
| `order_qty_1688` 총 수량 | 〃 |
| `intl_ship_per_unit` 개당 국제배송비 | 과세운임 |
| `exchange_rate` 실효환율 | 표시·감사용 |
| `buy_cny_total` 위안 합계 | 표시·감사용 |
| `pasted_at` 붙여넣은 시각 | 값이 언제 기준인지 |

조회할 때마다 이 순서로 계산한다:

```
개당 평균가 = buy_krw_total ÷ order_qty_1688
과세가격    = 개당 평균가 + intl_ship_per_unit
관세·부가세  = calcImportTax(과세가격, 조회 시점 관세율)
실효원가    = 과세가격 + 관세 + 부가세
손익분기가   = breakEvenPrice(실효원가, 물류 사이즈)
```

`exchange_rate`와 `buy_cny_total`은 계산에 쓰이지 않는다. 화면에 `¥8.00 = ₩1,768 (221.0원/위안)`을 함께 보여주고, 나중에 "그때 환율이 얼마였나"를 되짚을 수 있게 남긴다.

환율은 **그때 실제로 적용된 값**이므로 저장한다. 나중에 시장 환율이 변해도 이 주문의 원가는 그때 값이 맞다. 반면 관세율·수수료율처럼 정책이 바뀔 수 있는 값은 저장하지 않고 조회 시점 값을 쓴다.

`sourcing_shortlist`에 1688 관련 컬럼이 없으므로 마이그레이션이 필요하다.

## 국제배송비 — 유일한 수동 입력

붙여넣기가 채우지 못하는 값은 하나뿐이다. 화면의 `总运费`는 **중국 내에서 배대지까지** 가는 비용이고, 배대지에서 한국까지는 별개다.

`intl-shipping.ts`(해운 요율표·부피무게)가 있지만 **무게를 알아야** 쓸 수 있고, 1688 결제 화면에는 무게가 없다. 따라서 개당 배송비를 한 칸 직접 받는다.

**비워두면 경고를 띄운다.** 0으로 두면 1688이 실제보다 싸 보이고, 이는 낙관 방향 오류다 — 통과하면 안 될 후보가 통과한다.

## 판정

**도매꾹과 1688을 각각 낸다.** 원가가 다르니 손익분기도 판정도 다르다.

자동으로 싼 쪽을 고르지 않는 이유: 두 공급처는 **리드타임이 다르다**(국내 2~3일 vs 해운 약 30일 + 통관). 현금 회전과 재고 위험이 달라 단순 비교 대상이 아니다. 숫자는 양쪽 다 보여주고 판단은 사람이 한다.

---

## 화면

목업: 대화 중 공유한 아티팩트. 실제 파서와 원가 산식으로 동작한다.

- 소싱리스트 항목을 펼치면 **도매꾹 / 1688 두 줄**이 나란히 선다. 왼쪽 레일 색으로 구분하고(중립 / 주황), 각 줄에 리드타임을 적는다.
- 1688 줄에 붙여넣기 영역. 파싱하면 **검산 두 줄이 먼저** 뜨고, 통과해야 원가가 계산된다.
- 미달은 회색으로 낸다. 후보 대부분이 지나가는 정상 결과라 경고색을 쓰지 않는다.

## 오류 처리

| 상황 | 동작 |
|---|---|
| 검산 불일치 | 원가 계산으로 넘기지 않고 사유를 표시. 저장하지 않는다 |
| `合计` 또는 수량을 못 읽음 | "결제 확인 화면 전체를 다시 긁어와 주세요" |
| 원화(`₩`)가 없음 | 장바구니를 붙여넣었을 가능성이 높다 — 화면을 짚어 안내 |
| `价格明细`를 못 찾음 | 화면 우측 가격 영역까지 포함해 긁도록 안내 |
| 국제배송비 미입력 | 저장은 되되 "배송비 미반영 — 실제 원가는 더 높다" 경고 |
| 붙여넣기 저장 실패 | 버튼을 원복하고 사유 표시. 성공한 것처럼 두지 않는다 |

## 테스트

| 대상 | 확인 |
|---|---|
| 파서 | **실측 샘플 3건을 픽스처로 고정한다** (아래) |
| 검산 | 숫자를 하나 틀리게 만든 입력이 **거부되는가** |
| 장바구니 텍스트 | 원화가 없으므로 거부되는가 |
| 개당 평균 | 색상 변형 2개가 합쳐지는가 |
| 원가 | 실효원가·손익분기가 기존 산식과 일치하는가 |
| 저장·조회 | 환율이 보존되고 원가는 재계산되는가 |

**픽스처 3건이 서로 다른 경우를 덮는다.**

| 샘플 | 판매자 | 품목 | 배송비 | 쿠폰 | 특이 |
|---|---|---|---|---|---|
| 모자 | 1 | 색상 2 | ¥0.00 무료 | 있음 | 색상 변형 합산 |
| 수납袋 | 1 | 1 | **¥4.00** | 있음 | `服务 退货包运费` 비수치 행 |
| 파우치 | **2** | 각 1 | ¥2.00 | **한쪽만** | `店铺优惠 包邮` 비수치 값 |

이 셋이 아니었다면 놓쳤을 것들: 배송비 검산(모자만 봤으면 통과), 쿠폰 없는 품목(수납袋만 봤으면 `券后价` 필수로 가정), 판매자 복수(둘 다 단일 판매자).

파서는 순수 함수라 테스트하기 쉽다. UI는 `npm run build`로 검증한다 — 형제 탭에 렌더 하네스가 없다.

## 이 설계에서 제외한 것

| 항목 | 이유 |
|---|---|
| 장바구니 파싱 | 개당가가 확정되지 않는다. 위 참조 |
| 무게 기반 국제배송비 자동 산출 | 1688 화면에 무게가 없다. 발주 시점에 다룬다 |
| 색상별 개별 원가 | 소싱리스트 항목이 상품 단위다. 합쳐서 평균 |
| 1688 상품 URL 자동 추출 | 결제 화면에 상품 링크가 없다 |
| `DEFAULT_EXCHANGE_RATE_KRW_PER_RMB` 수정 | 별건. 마진 계산기 전반에 영향 |
| 자동으로 싼 공급처 선택 | 리드타임 차이를 숨긴다 |

## 열린 질문

**붙여넣기 텍스트가 브라우저·복사 방식에 따라 달라질 수 있다.** 설계는 결제 확인 화면 실측 샘플 3건에 기댄다(판매자 1~2명, 배송비 유무, 쿠폰 유무를 덮는다). 다른 브라우저나 확대/축소 상태에서 형태가 달라지면 파서가 실패할 수 있는데, 그때는 **검산이 막아준다** — 조용히 틀리는 대신 거부한다. 실패 사례가 쌓이면 파서를 넓힌다.
