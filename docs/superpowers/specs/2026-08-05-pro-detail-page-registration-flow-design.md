# PRO 상세페이지 ↔ 쿠팡 등록 연계 흐름

- **작성일**: 2026-08-05
- **상태**: ✅ **구현·검증 완료** (도미나스 크림 Ex, sellerProductId 16335592821)
- **배경 문서**: 위키 `상품 등록 자동화 현황 진단 2026-08-03`, `쿠팡 API 첫 등록과 버그 8건 2026-08-05`

## 문제

상품 등록을 Claude와 대화로 진행하면 재료 수집·마진 계산·고시정보 작성이 한자리에서 끝난다. 그러나 **상세페이지만은 PRO로 만들어야 한다** — 카피 엔진과 레이아웃 품질이 수기 HTML보다 낫다.

두 경로가 이어지지 않는다.

| 구간 | 현재 |
|---|---|
| Claude → PRO | PRO 계열 API가 전부 `requireAuth`라 Claude가 호출할 수 없다 |
| PRO → 쿠팡 | PRO 결과를 등록으로 넘기는 선이 없다 (진단 문서의 "③ PRO → 등록 연결") |

그리고 PRO의 입력 병목이 있다. `analyze-product`는 **이미지 + 상품명 + 카테고리코드**만 받는다. 사진에서 보이지 않는 정보(인체시험 수치, 특허번호, 시험기관, 브랜드 서사)는 들어갈 자리가 없어 결과가 일반론이 된다.

## 설계

### 흐름

| # | 담당 | 하는 일 | 산출물 |
|---|---|---|---|
| 1 | Claude | 대화에서 확보한 근거를 PRO 입력 형식으로 정리 | 상품명 1줄 · 핵심 판매 포인트 N줄 |
| 2 | 사용자 | PRO 첫 화면에 붙여넣기 + 이미지 3종 업로드 → 분석 → 편집 → **저장** | `detail_page_drafts` 레코드 |
| 3 | Claude | Supabase에서 최신 draft를 읽어 HTML 렌더 | 상세페이지 HTML |
| 4 | Claude | 쿠팡 `updateProduct`로 상세페이지 교체 → 조회로 반영 확인 | 교체 완료 |

**사용자 개입은 2번 한 곳뿐이다.** 텍스트는 붙여넣기, 이미지 선택은 어차피 사람의 일이다.

### PRO 첫 화면 입력 분담

| 입력 | 담당 | 비고 |
|---|---|---|
| 상품명 * | Claude | 쿠팡 등록명과 동일하게 유지 |
| 핵심 판매 포인트 (줄 구분) | **Claude** | 이 설계의 핵심 산출물 |
| 라벨 사진에서 정보 읽기 (최대 6장) | 생략 가능 | Claude가 이미 라벨을 읽어 고시정보를 확정한 경우 중복 |
| 참고 상세페이지 스크린샷 (최대 8장) * | 사용자 | Claude는 쿠팡 접근 불가 |
| 제품 이미지 (최대 4장) | 사용자 | 파일 선택 |

### 3번의 성립 조건

`/api/detail-page/render`는 `renderAllSections` 외에 후처리를 더한다. Claude가 직접 렌더할 때 **전부 동일하게 적용해야 한다.**

| 후처리 | 역할 | 누락 시 |
|---|---|---|
| `sanitizeProLayout` | claude_layout 섹션 정화 | 오염된 레이아웃이 등록됨 |
| `appendPrivacyFooter` | 개인정보 고지 3종 이미지 | **법정 표기 누락** |
| `composeYoutubeThumbnail` | 유튜브 썸네일 합성 | 해당 섹션 깨짐 |
| 팔레트·폰트 매핑 | theme → CSS | 디자인 불일치 |

**검증 방법**: 렌더 결과를 파일로 저장해 브라우저로 열고 PRO 화면과 육안 대조한다. 같으면 성립.

### 폴백

3번이 성립하지 않으면 **사용자가 PRO에서 HTML을 복사해 대화에 붙여넣는 방식**으로 떨어진다. 이 경로는 확실히 동작하므로 설계에 막다른 길이 없다.

### 채택하지 않은 안

**PRO 화면에 "쿠팡 반영" 버튼 추가.** 근본 해결이고 클릭 한 번으로 끝나지만 앱 개발이 필요하다. 3번이 성립하면 화면 수정 없이 같은 효과를 얻으므로, **3번 검증이 먼저다.** 3번이 실패하고 이 흐름을 반복해서 쓰게 되면 그때 만든다.

**첫 화면에 "Claude 입력 일괄 붙여넣기" 칸 추가.** 채울 칸이 텍스트 2개뿐이라 복사 2번이 1번으로 줄 뿐이다. 이득이 작아 보류한다.

## 재사용

도미나스 한 건이 아니라 **모든 신규 상품에 적용하는 표준 흐름**이다. 1번의 입력 형식을 고정해 두면 상품마다 대화에서 재료를 모아 같은 형식으로 뽑아낸다.

### 핵심 판매 포인트 작성 규칙

1. **사진에서 보이지 않는 것만 쓴다.** 색상·형태처럼 이미지가 이미 말하는 것은 PRO가 알아서 한다
2. **수치에는 출처를 붙인다.** 시험기관·기간·표본을 함께 적는다. 수치만 떼면 표시광고법 위험
3. **조건절을 버리지 않는다.** "3배"가 자사 이전 제품 대비면 그 조건을 함께 쓴다
4. **제조사가 표시한 문구를 벗어나지 않는다.** 라벨·패키지에 없는 효능을 만들지 않는다
5. 10~12줄 안으로 유지한다

## 검증 결과 (2026-08-05, 도미나스 크림 Ex)

| 검증 항목 | 결과 |
|---|---|
| `renderAllSections` 직접 호출 == API 응답 | ✅ **이미지 8개·순서까지 완전 일치** |
| draft 식별 | `detail_page_drafts`를 `updated_at` 내림차순으로 조회. 상품명으로 특정 가능 |
| `updateProduct`로 contents만 교체 시 나머지 보존 | ✅ 가격·재고·고시정보·갤러리 모두 보존 |
| 교체 후 재심사 | ⚠️ **자동으로 걸리고 자동으로 승인된다.** 수정 직후 잠시 `임시저장`으로 보이나 곧 `승인완료`로 복귀 |

**B안 성립이 확정됐다.** 사용자는 PRO에서 만들기만 하면 되고, HTML 복사·붙여넣기가 필요 없다.

### 작업 중 확인된 사실

| 사실 | 함의 |
|---|---|
| **PRO에 저장 버튼이 없다 — 자동저장이다** | 사용자가 "저장 버튼이 없다"고 한 시점에 이미 DB에 들어가 있었다 |
| 쿠팡은 상세설명의 외부 이미지를 **자기 CDN으로 재호스팅**한다 | 파일명이 해시로 바뀌므로 `frame-02` 같은 원본 파일명으로 검증하면 "누락"으로 오판한다 |
| 저장 후 `contentsType`이 `TEXT` → `HTML`로 재분류된다 | 조회 시 타입을 고정해 찾으면 내용을 놓친다 |
| 상세설명 수정은 **자동 재심사**를 거친다 | 승인 요청을 별도로 호출하면 `'임시저장' 상태의 상품만 승인 요청 가능` 오류가 난다 |

### 검증 방법에서 얻은 교훈

두 번 오판했고 원인이 같았다 — **조회 결과의 형태를 확인하지 않고 값만 봤다.**

1. `searchTags ?? []` → 필드가 없는데 "값이 0개"로 읽음
2. `contentsType === 'TEXT'` 필터 → 타입이 바뀌었는데 "HTML 0자"로 읽음

**조회로 판정할 때는 필드의 존재 여부와 값의 형태를 먼저 확인한다.**

## 승인 요청 API (2026-08-05 추가)

등록 직후 상태는 `SAVED`이며 승인 요청 없이는 판매가 시작되지 않는다. 앱에 이 경로가 없어 윙에서 수동으로 눌러야 했다.

| 추가 | 위치 |
|---|---|
| `requestApproval(sellerProductId)` | `src/lib/listing/coupang-client.ts` |
| `POST /api/listing/coupang/[id]/approve` | 신규 라우트. 인증 + 승인 후 상태 반환 |

**상세설명 수정 시에는 호출하지 않는다** — 자동 재심사가 걸리므로 오류가 난다. **신규 등록 직후에만 쓴다.**
