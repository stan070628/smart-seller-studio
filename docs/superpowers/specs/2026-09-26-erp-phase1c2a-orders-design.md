# ERP 1-C2a — 주문 수집과 판매 차감 설계

> **TL;DR** 쿠팡 판매자배송·쿠팡 RG·네이버·토스 주문을 15분마다 수집해 `erp.order_lines`에 쌓고, 결제된 라인을 원장에서 뺀다(판매자배송 = 집, RG = RG). 처음 3일은 기록만 하며 사용자가 채널 관리자 화면과 건수를 대조하고, 스위치를 켜면 기초재고 시각부터 소급 차감한다. 수집 라인은 옛 장부(`sale_records`)에도 기록해 수익·원가 화면을 버튼 없이 채운다.

- 작성: 2026-09-26 · 상위: `2026-09-25-erp-restructure-design.md` · 선행: 1-C1(PR #22, 기초재고 가동 — 기준 시각 2026-09-26 11:07:04 UTC)
- 결정 기록: `2026-09-26-erp-phase1c2-orders-decisions.md`

## 사용자 결정 (2026-09-26)

| # | 결정 |
|---|---|
| 1 | 1-C2를 둘로 — **1-C2a 주문 수집·판매 차감** · 1-C2b 당근 수동 판매·미귀속 대기열·RG 자동 입고 완료·이상 SKU 표시·옛 장부 버그 복구 |
| 2 | 판매자배송은 **결제 시 바로 차감**, 취소되면 역전표(설계서 원안의 할당→송장 반영 차감은 쓰지 않는다). RG 주문도 결제 시 RG 위치에서 뺀다 |
| 3 | **3일 기록 후 차감** — 사용자가 날짜별 건수를 채널 관리자 화면과 대조, 맞으면 스위치를 켜고 소급 |
| 4 | **새 수집이 옛 장부(`sale_records`)도 자동 기록** — 기존 「불러오기」 버튼은 새 경로로 바꾼다 |

## 1. 데이터

- `erp.orders`(채널 · 외부 주문번호 · 주문 시각 · 표준 상태 · 원래 상태 문자열) — 유니크 `(channel, external_order_id)`
- `erp.order_lines`(주문 · 채널 · **외부 라인 ID**(유니크 `(channel, external_line_id)`) · 리스팅 id(null 가능) · SKU id(null 가능) · SKU 기준 수량 = 주문 수량 × 배수 · 단가·금액 · 표준 상태 · 귀속 상태 `mapped|unattributed` · 차감 상태 `pending|posted|skipped_short|reversed` · 원장 키 · 옛 장부 행 id · 결제 시각 · 갱신 시각)
- **구매자 개인정보는 저장하지 않는다**(이름·주소·전화). 송장은 로지아이, 재고·매출에는 불필요
- 스위치: `erp.sync_cursors`와 같은 방식의 설정 행 `deduct_enabled`(기본 false). 채널별 수집 커서 `orders:<channel>`
- 채널 값: `coupang_wing` · `coupang_rg` · `naver` · `toss`(1-C2b에서 `karrot`)

## 2. 수집

| 채널 | 출처 | 라인 키 | SKU 연결 |
|---|---|---|---|
| 쿠팡 판매자배송 | 발주서 조회(상태별, **`nextToken` 끝까지**) | `shipmentBoxId:vendorItemId` | Wing vid → `channel_listings(coupang_wing)` |
| 쿠팡 RG | RG 주문 조회(끝 날짜 **포함**으로 구간 처리 — 옛 경계 버그 재발 금지) | `orderId:vendorItemId` | RG vid → `channel_listings(coupang_rg)` |
| 네이버 | 변경 주문 → 상품주문 상세(`moreSequence` 처리) | `productOrderId` | **원상품번호 + 옵션 ID**(클라이언트가 지금 버리는 `originalProductId`·`optionCode`를 살린다) |
| 토스 | 주문 조회(`nextCursor`) | `orderProductId` | **상품 ID + 옵션**(지금 이름만 받는 것을 ID로) |

- 15분마다 pg_cron → `/api/cron/orders-sync`(Bearer · `withJobRun` · 실패 시 텔레그램). 채널별 advisory lock
- 커서에서 **48시간 겹쳐** 다시 읽는다 — 상태 변경·늦은 취소를 놓치지 않게. 같은 라인은 갱신(upsert), 원래 상태 문자열 보존
- 첫 실행 시작점 = 기초재고 시각
- 채널 어댑터는 녹화한 응답(fixture)으로 테스트한다. 테스트 중 채널을 부르지 않는다

## 3. 차감

- 결제된 `mapped` 라인 → `postConsume(kind='sale')`: `coupang_rg` = `rg` 위치, 나머지 = `self`. 키 `sale:<channel>:<라인키>`(버전 붙으면 `@n`)
- 취소·반품(표준 상태) → 차감된 라인은 `reverse()`. 되돌린 라인이 다시 결제 상태가 되면 `@2`로 새로 차감
- `unattributed`(SKU를 가를 수 없음 — 네이버 옵션 없는 단일상품의 any_of 등)는 저장만, 차감하지 않는다(1-C2b 대기열)
- **재고 부족**이면 그 라인만 `skipped_short`로 두고 넘어간다. 다음 수집 때 다시 시도(재고를 고치면 풀린다)
- 스위치 off = 기록만. on으로 바꾸는 순간 기초재고 시각 이후 `pending` 라인을 결제 시각 순으로 소급 차감(SKU 오름차순 잠금)
- 기초재고 이전 결제 라인은 차감하지 않는다(기초재고가 이미 반영). SKU의 첫 전표가 opening이 아니어도(영수증·실사차이) 같은 규칙 — 기준은 전역 기초재고 시각

## 4. 옛 장부(`sale_records`)

- 수집 라인마다 한 행: 채널 `coupang`/`rocket_growth`/`naver`/`toss`, product_cost = SKU의 `legacy_product_cost_ids` 중 리스팅과 맞는 것(없으면 첫 값), 수량(배수 적용), 금액. 키를 채널별로 하나로 통일(`wing-…`/`rg-…`/`naver-…`/`toss-…`) — 판매자배송 이중 기록 제거
- 취소 → `voided_at`. 기존 불러오기 버튼(`rg-bulk-import`·`wing-bulk-import`·`naver-bulk-import`·상품별 `coupang-import`)은 새 수집 트리거로 바꾼다
- 과거 행(기초재고 이전) 복구는 1-C2b

## 5. 화면

- `/erp/stock` 위 **수집 현황 패널**: 채널별 오늘·어제·3일 건수 · 미귀속 · 마지막 수집 · 상태. 채널·날짜를 누르면 그날 라인 목록
- **「차감 켜기…」** 확인 창: 소급할 라인 수 · SKU 수 · 집/RG 감소량 → 승인해야 켜진다
- 입출 이력에 판매 전표(채널·주문번호). 재고 부족 라인 표시
- 기존 주문/매출 화면(채널 API 직접 조회)은 그대로 — 2단계에서 주문 표로 바꾼다

## 6. 작업 순서와 게이트

1. 마이그레이션 117 · 2. 순수 로직(연결·수량·상태 판정·키) · 3. 어댑터 4종(fixture) · 4. 수집기(잠금·겹침·upsert·옛 장부) · 5. 차감 모듈(스위치·소급·재고 부족) · 6. pg_cron + 수집 API · 7. 수집 현황 패널·차감 켜기 · 8. 기존 불러오기 버튼 교체 · 9. 테스트·빌드·리뷰·PR(병합은 확인 후)
- 🔴 **게이트 ①**(병합 직후~3일): 컨트롤러가 매일 날짜·채널별 건수표를 보이고 사용자가 채널 관리자 화면과 대조 — 3일 연속 일치
- 🔴 **게이트 ②**: 소급 합계 확인 → 사용자 승인 → 차감 켜기 → 재고현황·RG 대조(불일치가 판매·입고중으로 설명되는지)

## 하지 않는 것 (1-C2b 이후)

당근 수동 판매 · 미귀속 대기열 화면 · **RG 자동 입고 완료**(1-C2b 첫 작업 — 그전에는 PC 「입고 완료 옮기기」 수동) · 입고중 7일 경보 · 이상 SKU 표시 · 과거 RG 무효 1,062건·네이버 누락 복구 · 발주확인·송장 쓰기(로지아이 몫, 토스는 새 채널 확정 후) · 채널 재고 전송(1-D) · 주문 화면 교체(2단계)

## 열린 질문

- 새 판매 채널(2026-09-27 수업 후) — 어댑터 하나를 더하는 구조로 받는다. 로지아이 지원 여부에 따라 송장 쓰기 주체가 갈린다
- 네이버 번들·세트 상품(옵션 조합이 여러 SKU)의 라인 분해 — 리스팅 `bundle` 모드는 구성 SKU별로 차감(`listing_skus` 배수), `any_of`만 미귀속
